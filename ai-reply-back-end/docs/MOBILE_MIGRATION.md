# Переключение iOS и Android на бэкенд

## Что уже есть в приложениях

Обе сборки уже содержат абстракцию транспорта:

- iOS: `Shared/AI/ReplyTransport.swift`, `BackendTransport.swift`, `DirectOpenAITransport.swift`,
  переключатель `AIConfiguration.mode` (`.direct` / `.backend`), базовый URL в App Group,
  токен в Keychain (`SecureCredentialStore.backendToken`).
- Android: `ai/ReplyTransport.kt`, `BackendTransport.kt`, `DirectOpenAITransport.kt`,
  `AIConfiguration.mode`, токен в шифрованном хранилище (`SecureCredentialStore`).

Ключ OpenAI в исходниках отсутствует: в `direct`-режиме его вводит сам пользователь,
в `backend`-режиме он не нужен вовсе. Единственный экземпляр ключа в репозитории —
`AI-Reply/backend/.env` (в `.gitignore`), и он остаётся только на сервере.

## Шаг 1 — ничего не меняя

Новый бэкенд отдаёт старый контракт (`/v1/auth/register`, `/v1/reply/generate`)
байт в байт. Достаточно:

1. `AIConfiguration.setMode(.backend)` / `AITransportMode.BACKEND`;
2. base URL → адрес сервера (`https://ai-reply.kz` для iOS и Android).

После этого приложения перестают ходить в OpenAI напрямую, а запросы начинают
учитываться в квоте и статистике. Проверено тестами `TestLegacyEndpointsStayCompatible`,
`TestLegacyClientSharesQuota`, `TestLegacyMessageTooLong`.

## Шаг 2 — аккаунты и лимиты

Новый контракт `/api/v1/*` добавляет то, чего в старом не было: вход по номеру,
профиль на сервере, тарифы и остаток генераций.

Порядок работ (один и тот же на обеих платформах):

1. **Сетевой слой.** Один клиент: базовый URL, автоматическая подстановка
   `Authorization: Bearer`, единая обработка кодов ошибок, повтор запроса
   после `401` через `/auth/refresh` (ровно один раз, затем — выход).
2. **Хранилище токенов.** iOS — Keychain с общей группой доступа для приложения
   и клавиатуры (App Group + `kSecAttrAccessGroup`); Android — `EncryptedSharedPreferences`
   на Keystore, доступное и IME-сервису. Токены не пишутся в `UserDefaults`/`SharedPreferences`.
3. **Экраны входа.** Ввод номера (список стран берётся из `/api/v1/config`),
   экран кода (демо `1111`), завершение профиля — переиспользуя уже существующие
   компоненты онбординга и анкеты, без нового визуального языка.
4. **Тариф и остаток.** `GET /api/v1/me/usage` на старте и после каждой генерации;
   ответ `/ai/reply` уже содержит свежий `usage`, отдельный запрос не нужен.
5. **Состояния ошибок.** `DAILY_LIMIT_REACHED` → экран тарифов;
   `ACCOUNT_DISABLED` → выход; `AI_TIMEOUT` / `AI_PROVIDER_UNAVAILABLE` →
   «попробуйте ещё раз»; `UNAUTHORIZED` → тихий refresh.
6. **Клавиатура.** iOS-расширение не имеет собственной сети «по умолчанию» —
   оно читает токен из общей группы Keychain и делает запрос само;
   при отсутствии токена показывает подсказку открыть приложение.
   Android IME использует тот же `ServiceLocator`, что и приложение.
7. **Голос на Android.** `SpeechRecognitionClient` не трогаем: он распознаёт
   только инструкцию пользователя, и её текст уходит тем же полем
   `instruction` (`user_instruction` в старом контракте).

## Чего делать нельзя

- Не переносить ключ провайдера на устройство ни в каком виде.
- Не отправлять сообщения в мессенджеры автоматически: пользователь сам
  вставляет и отправляет ответ.
- Не обещать в онбординге чтение чужих переписок — ни iOS, ни Android этого
  не позволяют; клавиатура видит только скопированный или выделенный текст.
- Не хранить в приложении счётчик «сколько осталось» как источник истины —
  он справочный, решает сервер.

## Проверочный сценарий

1. Новый пользователь ставит приложение → видит онбординг на языке системы.
2. Вводит номер (KZ/RU/UZ/…), код `1111`, заполняет минимальный профиль.
3. Получает Free и 7 генераций в день.
4. Включает клавиатуру, копирует сообщение, диктует или пишет инструкцию.
5. Ответ приходит через бэкенд; текст нигде не сохраняется.
6. На 8-й генерации — корректная ошибка и экран тарифов.
7. Админ меняет лимит тарифа на 30 или 50 — приложение видит новый лимит
   без обновления в сторе.
8. Истёк access-токен → тихий refresh; logout отзывает сессию.
