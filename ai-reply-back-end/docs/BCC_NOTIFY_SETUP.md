# Настройка уведомлений BCC в backend

Обработчик подключён к основному Go-серверу и использует его действующий `APP_PORT`. Makefile, Docker Compose и настройки Caddy остаются прежними.

В основном серверном `.env` задаются:

```dotenv
BCC_SANDBOX_NOTIFY_ENABLED=true
BCC_TEST_NOTIFY_URL=https://ai-reply.kz:443/api/v1/payments/bcc/sandbox/notify
BCC_SANDBOX_NOTIFY_MANAGEMENT_TOKEN=<отдельный тестовый ключ управления>
```

Для текущего прогона отдельный ключ подготовлен в приватном файле настроек. Его не следует добавлять в Git или передавать банку. Если `PUBLIC_BASE_URL` использует другой домен, домен `BCC_TEST_NOTIFY_URL` должен совпадать с ним.

После обновления кода в `ai-reply-back-end` запуск обычный:

```sh
make docker
```

Проверка публичного маршрута:

```sh
curl --fail --silent --show-error https://ai-reply.kz:443/api/v1/payments/bcc/sandbox/notify/healthz
```

Ожидаемый ответ: `{"ok":true,"mode":"sandbox_capture_only"}`. Это проверка доступности, она не создаёт фиктивного банковского уведомления.

При включении обработчик создаёт отдельный `bcc-sandbox-notify.sqlite` рядом с основной SQLite, в том же постоянном Docker-томе. Обрабатываются только заранее зарегистрированные запросы тестового терминала `88888881`. Регистрация тестов и чтение уведомлений требуют отдельного Bearer-ключа.

По [документации BCC](https://documenter.getpostman.com/view/23274245/2s7YYo95nr#01cd529b-b069-4ad3-9971-f588124e6014) уведомление приходит как `application/x-www-form-urlencoded`: исходные параметры запроса и стандартные поля ответа. Обработчик сохраняет полный набор полей и исходное тело, сверяет заказ, тип, сумму, валюту, терминал, `NONCE`, `P_SIGN` и рекуррентные идентификаторы. Повторная доставка не создаёт вторую запись.

События сохраняются как `received_unverified`. Совпадение отражённого `P_SIGN` связывает уведомление с запросом, но не подтверждает отправителя; покупки по такому событию не начисляются. Результат проверяется отдельно серверным запросом `90`.

Basic Auth можно включить переменными `BCC_SANDBOX_NOTIFY_BASIC_USERNAME` и `BCC_SANDBOX_NOTIFY_BASIC_PASSWORD` после настройки тех же реквизитов на стороне банка.

После обновления сервера можно повторять банковские запросы с `NOTIFY_URL`. Старые запросы и результаты остаются неизменными.

## Новый поток покупки пакета

Старый приёмник из начала документа остаётся сборщиком банковского отчёта.
Для покупки пакета используется отдельный аутентифицированный callback и
изолированный контур; нельзя подключать сборщик как выдающий покупки webhook.

На существующем сервере изолированный маршрут включается отдельно:

```dotenv
BILLING_SANDBOX_ENABLED=true
BILLING_SANDBOX_BCC_ENABLED=false
```

Первый запуск не включает банковские запросы. Контур получает отдельную SQLite,
секреты авторизации и путь `/sandbox`; основной API и основные балансы остаются
в своём контуре. Не копируйте production-покупки или пользовательские данные в
стенд. Имена дополнительных переменных изолированного маршрута приведены в
актуальном `.env.example`; не переносите их значения в Git.

После согласования реквизитов с банком и проверки адреса callback заполните
**sandbox** merchant/terminal/MAC и отдельные случайные секреты. Основной
конфигурационный набор сервиса:

```dotenv
BCC_CHECKOUT_ENABLED=false
BCC_CHECKOUT_ENVIRONMENT=sandbox
BCC_CHECKOUT_PRODUCTION_APPROVED=false
BCC_SANDBOX_MERCHANT_ID=<merchant из документации банка>
BCC_SANDBOX_MERCHANT_NAME=<название мерчанта>
BCC_SANDBOX_TERMINAL_ID=<тестовый terminal>
BCC_SANDBOX_MAC_KEY=<sandbox MAC в HEX>
BCC_CHECKOUT_NOTIFY_USERNAME=<отдельное имя Basic Auth>
BCC_CHECKOUT_NOTIFY_PASSWORD=<отдельный случайный секрет не короче 32 символов>
BCC_CHECKOUT_STATE_SECRET=<другой случайный секрет не короче 32 символов>
```

На production основной `BCC_CHECKOUT_ENABLED` остаётся `false`.
Изолированный `/sandbox` использует настройки дочернего staging-контура и свой
отдельный переключатель `BILLING_SANDBOX_BCC_ENABLED`. Дочерний контур всегда
выбирает sandbox endpoint и sandbox-реквизиты, даже если основной checkout
настроен на production. Одинаковые Basic Auth должны быть настроены на стороне BCC.
Callback изолированного контура:

`https://ai-reply.kz:443/sandbox/api/v1/payments/bcc/notify`

Production-код имеет отдельные выключенные переключатели. Для его будущего
включения необходимы одновременно `APP_ENV=production`,
`BCC_CHECKOUT_ENVIRONMENT=production`, `BCC_CHECKOUT_ENABLED=true` и
`BCC_CHECKOUT_PRODUCTION_APPROVED=true`. Последний флаг — явное подтверждение
оператора после согласования с банком, а не автоматическая проверка договора.
Реквизиты читаются только из `BCC_PRODUCTION_MERCHANT_ID`,
`BCC_PRODUCTION_MERCHANT_NAME`, `BCC_PRODUCTION_TERMINAL_ID`,
`BCC_PRODUCTION_MAC_KEY`, `BCC_PRODUCTION_NOTIFY_USERNAME`,
`BCC_PRODUCTION_NOTIFY_PASSWORD`, `BCC_PRODUCTION_STATE_SECRET`.
Тестовые terminal/MAC и повторное использование настроенных sandbox-секретов
отклоняются. Нельзя подставить произвольный endpoint: production использует
только `https://3dsecure.bcc.kz/webview`. Callback основного контура —
`https://ai-reply.kz:443/api/v1/payments/bcc/notify` на домене `PUBLIC_BASE_URL`.
До подтверждения банка и полного теста платежа/уведомления/возврата production
остаётся выключенным. Локальные тесты используют фиктивные данные и не
подтверждают готовность банковского терминала.

Веб-кабинет `/sandbox/account` использует ту же тестовую БД и баланс, что
TestFlight 13. `/account` использует основную БД. В обоих случаях нужно войти
в тот же аккаунт; совпадение имени без подтверждённой почты не объединяет балансы.
После browser return сервер делает `303` на соответствующий `/payment?order=...`.
В URL передаётся только внутренний номер заказа, а не `ACTION`, `RC` или признак
успешной оплаты. Пакет появляется лишь после аутентифицированного финального
уведомления банка. Разовая покупка не создаёт подписку и не запускает автосписания.

`scripts/configure-billing-sandbox-env.py` предназначен для тестового контура:
он сохраняет основной `BCC_CHECKOUT_ENABLED=false`, не активирует production
и не изменяет `BCC_PRODUCTION_*`. Не используйте его как инструкцию включения
реального эквайринга.

### Необязательное push-предложение

Email-рассылка не добавляется. Предложение `web_topup_offer` относится только к
категории `marketing`: разрешение iOS на push само по себе не является согласием.
Нужно отдельно включить маркетинговое предложение в приложении. Backend создаёт
его один раз для аккаунта, когда есть подходящая зарегистрированная установка
iOS с токеном. Если согласие сохранено до APNs/FCM-регистрации, ключ однократности
не расходуется; регистрация токена повторяет проверку. Старые клиенты не участвуют:
требуется версия не ниже `1.2.0` и полностью числовой build не ниже `14`.
Перед отправкой вновь проверяются версия/build, согласие, включённый банк и
неизменность опубликованного предложения. Неподходящее или устаревшее предложение
не доставляется. Отметка однократности сохраняется в `notification_preferences`
до удаления аккаунта, независимо от очистки истории уведомлений и последующего
выключения/включения маркетинга. Если уже созданное предложение было пропущено
из-за отзыва согласия, изменения цены или доступности, автоматической повторной
рекламы не будет. Текст использует количество и цену из каталога и прямо называет
покупку разовой, без срока действия. Переход ведёт на `/payment` либо
`/sandbox/payment`; браузер открывается только по нажатию пользователя.

Все дополнительные флаги в исходном примере выключены:

```dotenv
WEB_TOPUP_OFFER_PUSH_ENABLED=false
BILLING_SANDBOX_PUSH_ENABLED=false
BILLING_SANDBOX_WEB_TOPUP_OFFER_ENABLED=false
```

Основной флаг предложения и два sandbox-флага независимы. Sandbox push требует
явного отдельного разрешения и настроенных Firebase-реквизитов того же приложения;
основные включённые push-настройки не включают его автоматически. При этом email
в sandbox остаётся выключенным, баланс/сессии остаются в отдельной БД и удаление
аккаунта не отзывает production-вход Apple. Включать рассылку можно только после
проверки сайта, банковской конфигурации и совместимого TestFlight-клиента. Наличие
кода и локальных тестов ничего не активирует и не отправляет.

### Принятие цены и условий на сайте

Перед созданием нового заказа сайт передаёт принятую версию каталога, цену,
количество, валюту и отдельную версию условий веб-покупки. `StartExpected`
повторно читает опубликованный каталог внутри транзакции создания заказа. При
изменении предложения или условий возвращается конфликт без создания оплаты.
Запись принятого предложения в `billing_web_purchase_consents` и банковский заказ
коммитятся вместе. Повторный запрос с тем же пользовательским ключом возвращает
исходный заказ и не заменяет его цену/условия новой публикацией.

### Вход на сайт из приложения

Авторизованное приложение может запросить `POST /api/v1/web/payment-handoff`
с bearer-токеном, `expected_user_id` текущего аккаунта и `locale`. Сервер сначала
сверяет получателя с авторизованным пользователем. Ответ содержит только
`url` и `expires_in=60`: HTTPS-адрес `/payment#handoff=...` (либо
`/sandbox/payment#handoff=...`). Это отдельный случайный 256-битный код на одну
попытку, не access/refresh-токен приложения. Генерация ограничена пятью запросами
в минуту на пользователя. В БД `web_auth_handoffs` хранится только SHA-256 кода;
просроченные/использованные строки удаляются ограниченными пакетами при создании
новых ссылок. При удалении аккаунта его коды удаляются каскадно.

Сайт сразу убирает fragment из адресной строки, держит код только в памяти и
обменивает его через `POST /account/api/handoff` с существующей проверкой Origin
и `X-Requested-With`. Код нельзя сохранять в localStorage или писать в журнал.
Анонимный браузер либо браузер того же аккаунта получает отдельную HttpOnly
веб-сессию. Если браузер уже вошёл в другой аккаунт, сервер отвечает
`409 WEB_ACCOUNT_SWITCH_REQUIRED`, показывает обе почты и не расходует код до
явного `confirm_account_switch=true`. Старую веб-сессию закрывают только после
успешного обмена; сессия приложения остаётся самостоятельной.

Обмен атомарно проверяет срок, однократность и активность аккаунта. Повтор,
подмена, удалённый/отключённый аккаунт и истёкший код дают одинаковый
`WEB_HANDOFF_INVALID`; браузер может войти обычным кодом по почте или пользователь
может открыть новую ссылку из приложения. Код основного контура не работает в
sandbox и наоборот. Переход только авторизует: он не создаёт заказ, не принимает
условия покупки и не начисляет ответы. Снимок сайта содержит лишь идентификатор/
почту аккаунта, тариф, баланс и банковское предложение, без бизнес-профиля и
согласий на AI-обработку. Нативный `/me` сохраняет прежний контракт.

Точный домен берётся из `PUBLIC_BASE_URL`, URL всегда HTTPS с явным `:443`.
MAC-ключ, пароль уведомлений и state-секрет остаются только на сервере.
Приложение получает только URL hosted checkout; карточные данные вводятся на
странице банка. Локальный журнал приложения записывает только URL.Path, без
query-параметра state. Reverse proxy также должен исключать query state из
access log для `/sandbox/api/v1/payments/bcc/orders/*`.

Порядок проверки:

1. В `/sandbox/admin/billing` проверить опубликованный `pack30`: 30 ответов,
   100 ₸, Web доступен. Подписка для покупки не нужна.
2. Авторизовать тестовый аккаунт в `/sandbox/api/v1/*`.
3. Отправить `POST /sandbox/api/v1/payments/bcc/checkout` с JSON
   `{"product_code":"pack30"}` и новым стабильным `Idempotency-Key`.
4. Открыть возвращённый `redirect_url`; вручную перейти на банковскую форму.
   Использовать только официальные тестовые карты и процедуры из предоставленной
   документации BCC; реальные карты и production merchant не применяются.
5. Проверить `GET /sandbox/api/v1/payments/bcc/orders/{payment_id}/status`.
   Возврат браузера — `verification_pending`, финальный аутентифицированный
   банковский callback — `succeeded`. Только затем остаток увеличивается на 30.
6. Проверить второй пакет и повторную доставку того же callback. Баланс
   накапливается, повторная доставка ничего не добавляет.
7. Выполнить явный полный sandbox-возврат кнопкой администратора и проверить
   отзыв только неиспользованной части соответствующего пакета.

До фактического исполнения этих шагов реальная sandbox-покупка, доставка
уведомления и банковский возврат считаются непроверенными. Локальные unit и
integration fixtures не заменяют банковский прогон. Банковские автоматические
подписки, partial refund и production BCC остаются выключенными.

### Обязательные реквизиты CARD / 3-D Secure

Перед переходом на банк hosted checkout собирает реальный телефон держателя
карты (код страны и номер) и первую строку платёжного адреса, максимум 50
символов. Скрипт формирует `M_INFO` как UTF-8 JSON в Base64: фактические
`screen.height`, `screen.width` передаются строками, вместе с `mobilePhone` и
`billAddrLine1`. Образцы телефона/адреса из документации не подставляются.
Телефон и адрес уходят прямо в BCC, в заказе и журнале backend не сохраняются.
`CLIENT_IP` берётся при открытии страницы из существующего trusted-proxy
механизма `httpx.ClientIP`, а не из клиентского JSON; `0.0.0.0` отклоняется.
Для скрипта устанавливается отдельный CSP nonce без `unsafe-inline`.

Сервер формирует обязательный `MERCH_RN_ID` длиной 16 алфавитно-цифровых
символов и сохраняет его для исходной операции и возврата. `MERCH_NAME`
соответствует банковскому формату: верхний регистр латиницы, не более 21
символа. В CARD-потоке не придумываются поля COUNTRY/MERCH_URL или данные
TOKEN-покупки; EMAIL обязателен в документированном TOKEN-потоке, который этот
one-time CARD checkout не использует. Полный возврат дополнительно отправляет
исходный `MERCH_RN_ID`, `MERCH_GMT=0` и `LANG` по шаблону `14`.
