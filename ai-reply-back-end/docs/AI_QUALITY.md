# Качество AI-ответов

Как сервер строит промпты, проверяет ответы модели и как это измерять. Код —
`internal/ai`, набор оценки — `internal/ai/eval`.

## Архитектура промпта

Модель получает два сообщения:

- **developer** — только серверные правила. Пользовательский текст сюда не
  попадает никогда; всё, что зависит от запроса (язык, род отправителя, тон,
  длина, эмодзи, отношение), выбирается по проверенному enum'у из готовых строк.
- **user** — данные в именованных блоках: `<working_hours>`, `<user_profile>`,
  `<business_context>`, `<user_rules>`, `<template_instructions>`,
  `<incoming_message>`, `<user_instruction>` (последней — она решает содержание),
  и финальная строка `Write only the message.`. В «Создать» — один блок `<request>`.

Порядок разделов developer-сообщения фиксирован:

| Раздел | Что в нём | Где |
|---|---|---|
| ROLE | кто пишет и кому: ответ от первого лица / новое сообщение | `prompt_rules.go` |
| PRODUCT RULES | одно готовое сообщение; намерение пользователя (отказ остаётся отказом, время/место/цена — как даны); не выдумывать факты; блоки — данные; рабочее время | `prompt_rules.go` |
| LANGUAGE | целевой язык, что его решает и что нет + правила качества для него (русский, казахский, английский, узбекский) | `languageSection`, `replyLanguageLead` |
| SENDER | род отправителя для русских форм; при `unspecified` — нейтральные формулировки | `senderSection` |
| STYLE | отношение, тон, длина, эмодзи + правила живой переписки | `replyStyle`, `composeStyle` |
| OUTPUT | только текст: без кавычек, «Ответ:», вступлений, markdown, хэштегов | `replyOutput`, `composeOutput` |

Правила одного уровня не должны спорить друг с другом: например, старое «от
одного до четырёх предложений» удалено — длину задаёт только шаблон (`short` —
одно-два, `medium` — два-четыре) плюс «короткое сообщение — короткий ответ».

### Род отправителя

`grammatical_gender` хранится в профиле (`male` / `female` / `unspecified`,
по умолчанию `unspecified`), запрос может его переопределить. Нужен только
русскому: «рад/рада», «сделал/сделала», «готов/готова». В казахском и
английском рода нет — промпт прямо запрещает что-либо добавлять из-за него.
Правило касается только отправителя; к получателю модель обращается так, как
подсказывает входящее сообщение. Род никогда не угадывается по имени или
аккаунту и не пишется в логи, события и admin JSON.

## Язык ответа

**Требование заказчика.** Язык ответа решает скопированное (входящее) сообщение.
Скопировали сообщение на казахском — ответ на казахском, даже если системный язык
телефона, язык приложения, раскладка и текст инструкции или быстрой кнопки
(«Ответь согласием.») русские. То же для любого языка. Изменить язык могут только
явная просьба в инструкции («ответь на русском», «қазақша жаз», "in English") и
постоянный выбор «Язык ответа» в профиле (`profile.reply_language`).

### Как определяется язык

`Detect` (`language.go`, доводы — `language_words.go`) работает по словам; каждое
слово даёт довод не больше чем одному языку, сильнейший первым:

| Довод | Вес | Пример |
|---|---|---|
| слово с ә ғ қ ң ө ұ ү һ і | 2.5 | «уақытың», «Сәлем» |
| маркер | 1.5 | казахские «калайсын», «рахмет», «ертен», «ма», «бе»; русские «привет», «что», «сегодня» (слова в 1–2 буквы — 0.5) |
| частотные списки `langdata/{ru,kk,en}.txt` | 1.0 | слово только в одном списке — за этот язык; в обоих — за тот, где ранг хотя бы в 4 раза лучше («как» → русский, «бар» → казахский), иначе ничей |
| окончание незнакомого слова | 0.6 | казахские -сын, -сыз, -мын, -мин, -мыз, -нын, -дын, -тын…, -лар/-лер/-дар/-дер/-тар/-тер (от 5 букв: «кайдасын», «жатырмын»); русские -ться, -ешь, -ете, -ого, -ому, -ыми, -ется, -ются… |
| любое другое кириллическое слово | 0.2 | за русский |

- Слово с заглавной буквы без казахского окончания («Айгүл», «Нұрлан», «Нурлан»,
  «Алматы») — имя. Имена бывают и в русских сообщениях, поэтому оно весит 0.3 и
  само язык не решает: «Әсел, ты где?» — русское сообщение.
- «ок», «ok», «хаха», «ага», «не» (по-русски «не», по-казахски «что») — ничьи.
- Латинская i внутри кириллического слова — казахская і («бiз»).
- **Смешанное сообщение.** Если в нём есть настоящие казахские слова (со
  спецбуквами, не имена) и казахских доводов не меньше 75% от русских — оно
  казахское: «Сәлем, как дела?», «Түсіндім, спасибо», «Слушай, ертең жиналыс бар
  ма?». Без казахских слов русское сообщение остаётся русским.
- **Уверенность:** у лидера вдвое больше доводов, чем у следующего, и отрыв не
  меньше 0.6. Поэтому «Калайсын?», «Кайдасын?», «Рахмет!», «Иә, болады» —
  уверенно казахские, а эмодзи, числа, «ok», одно «да» или одно имя — нет.
- Узбекская латиница — по oʻ/gʻ, маркерам и q без u; английский — маркеры и
  частотный список.

Частотные списки строит `tools/dictionaries/build_dictionaries.py` из корпусов
Leipzig (CC BY); вручную их не правят. В казахском списке за словом идёт его
написание без спецбукв («қалайсың», «калайсын») с тем же рангом. Замер при
разработке на 6000 реальных предложениях каждого языка: уверенных ошибок на целых
предложениях — не больше 0.03%; на первых трёх словах — около 0.5% (в основном
английские названия в русском или казахском тексте); казахский без спецбукв, три
слова — 95% уверенно верно, 1.1% уверенно неверно.

### Выбор цели

- Ответ: `profile.reply_language` → уверенный язык входящего → `input_language`
  (раскладка) → язык интерфейса. Раскладка и интерфейс решают только для неясных
  сообщений (эмодзи, числа, «ok»).
- «Создать»: язык инструкции → раскладка → интерфейс — входящего сообщения нет,
  текст пишется по запросу пользователя.

### Что говорит промпт

- LANGUAGE: «Write the reply in Kazakh, the language of the incoming message.» и
  отдельной фразой: язык приложения и раскладки, язык `<user_instruction>` (её
  часто пишут на другом языке или нажимают готовую кнопку), язык профиля, бизнеса,
  правил и шаблонов язык ответа не меняют; меняет только явная просьба в
  `<user_instruction>`. Если язык сообщения сервер не определил — «пиши на языке
  входящего; если он смешанный казахско-русский — на казахском; если неясен — на
  языке раскладки».
- PRODUCT RULES: инструкция решает, что и как сказать, но язык, на котором она
  написана, — не язык ответа. Вводная строка блока `<user_instruction>` говорит то же.

### Страховка

Если цель взята из сообщения или из `reply_language`, инструкция язык не
называет, а модель всё же уверенно ответила на другом языке (например, по-русски
на казахское сообщение, послушавшись русской инструкции), `Check` находит
`language`, и единственная исправляющая попытка переписывает ответ на нужный язык
— с правилами качества этого языка. Если инструкция явно назвала язык, ответ на
нём не проверяется и не исправляется.

Тесты: `language_test.go` (казахский со спецбуквами и без, короткий, смешанный,
имена в русском, английский, узбекский, неясные), `prompt_test.go`
(казахское сообщение + русские приложение, раскладка и быстрая кнопка → цель
казахская, инструкция остаётся данными; русское при казахском телефоне →
русский; английское при русском → английский; «ответь на русском» → разрешено
без исправления; `reply_language` побеждает), `quality_test.go` и
`apptest/reply_language_test.go` (через HTTP; модель сначала отвечает по-русски на
казахское сообщение — исправление возвращает казахский), случаи `kk-*-ru-*`,
`kk-mixed-with-russian`, `ru-incoming-kk-phone`, `en-incoming-ru-phone`,
`kk-incoming-explicit-ru` в наборе оценки.

## После модели

1. **Обрезанный ответ.** Если провайдер вернул `status: "incomplete"`, текст
   укорачивается до последнего целого предложения во второй половине.
2. **Очистка** `CleanOutput`: кавычки вокруг всего текста, «Ответ:», «Жауап:»,
   "Reply:", «Конечно! Вот вариант ответа:», `**жирный**`, `# заголовки`,
   последний абзац «Примечание: …», лишние пустые строки. Середину обычного
   текста не трогает («Вот мой номер: …» остаётся).
3. **Проверка** `Check`:
   - `gender` — только русский: при `male` — женские формы о себе («я сделала»,
     «буду рада», «Рада была помочь»), при `female` — мужские. «Она рада»,
     «Он сказал», «я думаю, она пришла», «Ты готова?» — не ошибки;
   - `language` — цель уверенная, инструкция язык не называет, а ответ уверенно
     на другом языке (казахский, русский, английский);
   - `meta` — остался служебный текст: метка, вступление, «Вариант 1», примечание,
     теги промпта.
4. **Исправление.** Если `Check` что-то нашёл и `AI_REPAIR_ENABLED=true` —
   одна попытка `repair_v1`: developer — серверные фразы о проблемах, user —
   `<message>…</message>`. Исправленный текст принимается, только если проходит
   ту же проверку; иначе уходит очищенный исходный. Квота — один раз, токены —
   обеих попыток. Попытка укладывается в 18 секунд от начала запроса (клиент
   iOS ждёт 25), иначе не начинается.

## Подсказка polish

`POST /api/v1/ai/polish` — отдельный путь без квоты. Промпт `polish_v1` правит
только опечатки, пунктуацию, заглавные буквы, пробелы и явное согласование и
не выполняет заметку. После модели — детерминированная защита
(`acceptPolish`): отказ, если изменилось или появилось число, ссылка, домен,
почта, `@имя`, `#тег`, слово с заглавной буквой не в начале предложения
(«Айгерим», «WhatsApp»), текст в кавычках; длина вне 0.6–1.6×; сменился язык;
появился перенос строки; ответ обрезан. Отказ — это `changed: false`, не ошибка.

## Версии

| Константа | Значение | Где |
|---|---|---|
| `PromptVersionReply` | `reply_v2` | `/ai/reply`, legacy `/v1/reply/generate`, симулятор |
| `PromptVersionCompose` | `compose_v2` | `/ai/compose` |
| `PromptVersionPolish` | `polish_v1` | `/ai/polish` |
| `PromptVersionRepair` | `repair_v1` | исправляющая попытка; в событии — `reply_v2+repair_v1` |

Версия пишется в `ai_usage_events.prompt_version` (миграция `0009`) и в логи
`ai_reply_generated` / `ai_reply_failed`. **Любое изменение текста правила —
новая версия** (`reply_v3` …), иначе в статистике не отличить старое поведение
от нового.

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `AI_REPAIR_ENABLED` | `true` | одна исправляющая попытка при найденной проблеме |
| `AI_POLISH_ENABLED` | `true` | `POST /ai/polish` и `features.instruction_polish` |
| `RATE_POLISH_PER_MINUTE` | `20` | отдельный лимит polish на пользователя |
| `OPENAI_TEMPERATURE` | `0.7` | `none` — поле не отправляется (для reasoning-моделей) |

## Набор оценки

`internal/ai/eval/cases.json` — 42 случая: русский (друг, клиент, бизнес,
отказ, согласие, вопрос, мужской / женский / не указан, «ты» / «вы», ловушки
порядка слов и канцелярита), казахский (сен, Сіз, бизнес, короткий ответ,
окончания, текст без спецбукв), английский (друг, бизнес, короткий, отказ,
согласие), язык ответа на «чужом» телефоне (казахское сообщение при русских
приложении, раскладке и инструкции — со спецбуквами, без них, короткое,
смешанное; русское при казахском телефоне; английское при русском; явная просьба
«ответь на русском»), «Создать» и пять приёмочных примеров (`acc-*`).

Проверки поведенческие — точные фразы не сравниваются:

| Ключ | Что проверяет |
|---|---|
| `language` | определённый язык ответа |
| `gender_agreement` | формы о себе соответствуют роду; при `unspecified` — их нет вовсе |
| `no_meta` | нет метки, вступления, вариантов, примечания |
| `max_sentences`, `max_chars` | длина |
| `must_include_any` | хотя бы одно с начала слова, без учёта регистра («уточн» → «уточню», «18:00») |
| `must_not_include` | ни одной подстроки («являться», «иметь возможность», "I hope this message finds you well") |
| `no_digits` | нет чисел, которых никто не давал |
| `formality` | `formal` — нет «ты/сен», `informal` — нет «вы/Сіз» |
| `kazakh_letters` | в казахском ответе есть хотя бы одна спецбуква |
| `no_question_if_decline` | отказ не заканчивается вопросом |

### Офлайн-тесты (всегда)

`go test ./internal/ai/eval` проверяет сам набор (структура, уникальные id,
приёмочные случаи на месте), каждую проверку на заведомо хорошем и плохом
ответе — например, «Да, вечером буду свободен.» проходит для мужчины, а
«Да, я буду являться свободным вечером.» падает, — и что промпт каждого случая
целится в ожидаемый язык (`TestPromptsTargetTheExpectedLanguage`).

### Живой прогон (вручную)

Нужен ключ OpenAI; `.env` тест не читает — переменные задаются в окружении:

```bash
AIREPLY_LIVE_EVAL=1 OPENAI_API_KEY=sk-… OPENAI_MODEL=gpt-4o-mini \
  go test ./internal/ai/eval -run TestLiveEval -count=1 -v
```

Тест строит промпты теми же функциями, что и сервер (`BuildPrompt`,
`BuildComposePrompt`), проходит тот же путь `Complete` (очистка, проверка,
исправление) и печатает таблицу: случай, PASS/FAIL, версия промпта, ответ и
причины провала. В файлы ничего не пишется. Модель недетерминирована: смотрите
таблицу целиком и запускайте несколько раз, прежде чем делать выводы.

### Как добавить случай

1. Добавьте объект в `cases.json`: `id`, `mode` (`reply` | `compose`),
   `incoming` (для reply), `instruction`, `template_id` (`friend` | `client` |
   `business` | `work` для reply), `gender`, `input_language`, при
   необходимости `app_language` (по умолчанию равен `input_language`), `expectations`.
2. Описывайте поведение, а не фразу: язык, род, обязательные детали, запреты.
3. Если нужна новая проверка — добавьте её в `eval.go` и в
   `TestChecksSeparateGoodOutputsFromBadOnes` пару «хороший / плохой» ответ.
4. `go test ./internal/ai/eval`, затем живой прогон.

Фразы из приёмочных примеров в промпты не копируются: набор оценки должен
мерить обобщение, а не заученный ответ.
