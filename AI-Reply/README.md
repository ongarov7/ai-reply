A local iOS proof of concept: a Custom Keyboard Extension that is comfortable to
type on in EN / RU / KK and that can pick up "the message the user wants to act
on" through supported iOS APIs only.

No AI, no networking, no analytics, no authentication, no backend, no
third-party dependencies.

## Status: AI MVP

The proof of concept is now an AI-powered keyboard. Replies are generated by
**OpenAI `gpt-4o-mini`**, using a personal communication profile, a relationship
template and optional working-hours context that the user configures in the host
app.

### The credential

The app calls `api.openai.com` **directly**. There is no proxy in the request
path.

The key is **not** in the source, the Info.plist, an xcconfig, UserDefaults, App
Group storage, a bundled resource, or the IPA. It is pasted into the app once,
at runtime, and stored in the **iOS Keychain** (device-only, never synced). A
build of this project therefore contains no secret, and the security rules in
the brief all still hold.

Enter it in **Settings ▸ OpenAI ▸ API key**, or during onboarding. There is a
one-tap Paste button, because typing a 164-character key on a phone is not a
reasonable thing to ask.

> The trade-off, stated plainly: a key on a device is extractable by whoever
> holds that device, and every request is billed to it with no limit but
> OpenAI's own. That is fine for a demo on your own phone. It is not fine for
> the App Store. `backend/` holds a complete server for that case — see
> [Optional backend](#optional-backend).

### Flow

```
copy a message in WhatsApp / Telegram / Instagram
        ↓
open the AI Reply keyboard
        ↓
tap a template:  ✨ │ Friend │ Client │ Business │ Work    (✨ writes a new message instead)
        ↓                         ← the ONLY thing that starts a request
read clipboard  ·  check ≤ 300 characters  ·  build prompt
        ↓
POST https://api.openai.com/v1/responses      (gpt-4o-mini)
        ↓
editable draft  →  edit  ·  ↻ regenerate
        ↓
Insert  →  textDocumentProxy.insertText
        ↓
YOU press Send. The app never sends anything.
```

### What the model is told

Three things, plus the message:

| Piece | Source | Cap |
|---|---|---|
| Role ("what do you do?") | profile | 120 chars |
| Communication profile ("about me") | onboarding, typed or dictated | 1000 chars |
| What you sell / provide | profile, and per template | 120 chars |
| Business description | profile, and per template | 400 chars |
| Rules ("never promise X") | profile, and per template | 8 × 200 chars |
| Relationship template | built-in behaviour + user instructions | 600 chars |
| Working-hours context | derived from the device clock | — |
| Incoming message | clipboard, on explicit tap | **300 chars** |

Template answers win over profile answers for the same question; the profile
still supplies whatever the template left blank. Rules from both levels are
merged and de-duplicated.

The 300-character limit applies to the **incoming message only**. Profile and
template text are separate and do not count against it.

Working-hours context is derived, never located: the model is told
`isWithinWorkingHours`, the local wall-clock time and when the next window
opens. No timezone name, no city, no coordinates.

### Prompt safety

The rules live in the **developer** message and nothing user-controlled is ever
concatenated into it. The copied message, the profile and custom template
instructions go in the **user** message inside named blocks, introduced as data.
A message reading "Ignore previous instructions" is a message that says that —
quoted, not obeyed. Verified: `Tests/AIReplyServiceTests.swift`, and against the
live model.


## 1. Audit of the previous implementation

| Finding | Detail |
| --- | --- |
| Chrome ate half the keyboard | Fixed height 368pt. Toolbar 34 + preview 92 + Insert 30 + stack margins/spacing 30 = **186pt (50.5%)** of chrome. Only **182pt** was left for the keys. |
| Keys were undersized | 182pt / 4 rows ⇒ ~41pt keys in EN/RU. Kazakh used 5 rows ⇒ **~31.6pt keys**, well below the ~42pt native key. |
| Forced light appearance | `view.overrideUserInterfaceStyle = .light` plus a hard-coded near-white palette. This is why the keyboard was white inside dark Telegram. |
| Weak height constraint | The height constraint used `.defaultHigh` (750). It happened to win, but 999 is the correct priority for an input view. |
| Debug UI shipped in the product | `Full Access: … · Clipboard: …` was inside `#if DEBUG`, but a debug build on a real device still shows it, and it was in the screenshot. |
| Config/background conflict on keys | Keys mixed `UIButton.Configuration` with direct `backgroundColor`, so the highlight state was applied twice and could disagree. |
| Touch model | Everything fired on `.touchUpInside`, so typing felt laggy versus the system keyboard, and there was no delete repeat. |
| Localization | All strings were English literals inside `KeyboardViewController`. |
| Russian row 3 | 10 letters plus shift and delete on a 12-column grid, which squeezed shift and delete to letter width. |

**Root cause of the small keyboard:** the permanent preview card, the three-button
debug toolbar and the permanent Insert button were laid out as siblings of the
key stack inside a fixed 368pt view, so every point they took came directly out
of the keys.

## 3. Height and layout strategy

Nothing is hard-coded to one device. `KeyboardMetrics` takes the live
`view.bounds.width` and the number of rows the current layout needs.

```
keyHeight   = 48  (width ≥ 410)   |  46 (width ≥ 375)  |  43 (smaller)
             ×0.855 when the layout needs 5 rows (Kazakh)
rowGap      = 11 for 4 rows, 8 for 5 rows
columnGap   = 6 (width ≥ 375) else 5
total       = actionBar(42) + 3 + 5 + rows + 5
```

Measured on a 393pt-wide iPhone:

| Layout | Rows | Key height | Total height | Typing share |
| --- | --- | --- | --- | --- |
| EN / RU letters | 4 | 46pt | 272pt | **83.5%** |
| Kazakh letters | 5 | 39pt | 282pt | **84.1%** |
| Numbers / symbols | 4 | 46pt | 272pt | 83.5% |
| *(previous build)* | 4 | 41pt | 368pt | *49.4%* |

The keyboard is now **shorter overall** and the keys are **taller**. The height
constraint sits at priority 999 on the input view.

The reply composer grows the action bar and grows the keyboard by the same
amount, so the typing area is never reduced — not even temporarily. Key height is
identical in every state below:

| State | Bar | Keyboard (EN, 393pt) | Key height |
| --- | --- | --- | --- |
| Idle | 42pt | 272pt | 46pt |
| Composer, 1-line source, empty draft | 88pt | 318pt | 46pt |
| Composer, 2-line source, empty draft | 103pt | 333pt | 46pt |
| Composer, 2-line source, 2-line draft | 119pt | 349pt | 46pt |
| Composer, source expanded + 3-line draft | 155pt | 385pt | 46pt |

The "typing share" target of 80–90% applies to the idle keyboard. While the
composer is open the share drops (68% in the common case) purely because the
keyboard got taller — not one point comes out of the keys.

`viewWillLayoutSubviews` re-renders whenever the width changes, so rotation and
every iPhone width (SE through Pro Max, Dynamic Island models included) are
handled by the same code path.

## 4. Dark theme

The appearance follows `UITextDocumentProxy.keyboardAppearance`, which is what
Telegram, WhatsApp and Instagram actually set when they are in dark mode; the
trait collection is only the fallback when the host says `.default`. It is
re-resolved in `textDidChange`, so switching the host's theme while the keyboard
is up updates it.

| Role | Dark | Light |
| --- | --- | --- |
| Backdrop | `#1B1B1D` | `#D1D4DA` |
| Letter key | `#4A4A4E` | `#FFFFFF` |
| Special key (shift, delete, 123, globe, language, return) | `#2C2C30` | `#ACB0BA` |
| Engaged shift / caps lock | `#EFEFF2` with dark glyph | `#FFFFFF` with dark glyph |
| Text | white | black |

Pressing a letter key darkens it to the special shade and pressing a special key
lightens it to the letter shade, which is what the system keyboard does. No
gradients, no borders, no large shadows — only a 1pt hard bottom edge.

## 5. Localization

There are **two** languages in this product and they answer different questions.
Collapsing them into one was the bug this iteration fixed: the app was set to
Kazakh and the keyboard row still read `Friend | Client | Business | Work`.

| Concept | Follows | Lives in | Examples |
| --- | --- | --- | --- |
| **App / product language** | iOS preferred languages, overridable in Settings ▸ Language | `AIReplyStrings` (keyed by `AppLanguage`), `Localizable.xcstrings` | template chips, Insert, Regenerate, statuses, errors, every host-app screen |
| **Keyboard layout** | the language key on the keyboard | `KeyboardStrings` (keyed by `KeyboardLanguage`) | the character keys, `space`, `return`, the layout badge |

A Kazakh user typing on the Russian layout to write a Russian reply sees
`Кірістіру` on the blue button and `пробел` on the space bar. Both are correct.
The type system enforces it: `AIReplyStrings` cannot be reached from a
`KeyboardLanguage`, so a product label cannot be resolved from the layout by
accident.

**First launch.** `AppLanguage.systemDefault` reads `Locale.preferredLanguages`:
a code beginning `kk` gives Kazakh, `ru` gives Russian, anything else gives
English. No GPS, no SIM, no IP, no region.

**Override.** Settings ▸ Language writes to the App Group, so the keyboard picks
it up. The keyboard caches the value in memory and re-reads it only when it
appears — never on a keypress.

## 6. Layouts

### English — 10 / 9 / 7

```
q w e r t y u i o p
 a s d f g h j k l
⇧  z x c v b n m  ⌫
123  🌐  EN  ␣  return
```

Row 2 is centred on the 10-column grid; shift and delete take the leftover width
(~53pt on a 393pt screen).

### Russian — 12 / 12 / 9

```
й ц у к е н г ш щ з х ъ
ф ы в а п р о л д ж э ё
⇧  я ч с м и т ь б ю  ⌫
123  🌐  РУ  ␣  ввод
```

One deliberate deviation from Apple's Russian keyboard: **`ё` is placed at the
end of row 2 instead of behind a long press on `е`.** Every Cyrillic letter is
therefore visible, and row 3 keeps only 9 letters so shift and delete stay ~43pt
wide instead of collapsing to letter width (~27pt). Rows 1 and 2 both hold 12
keys, so the grid lines up.

### Kazakh — 9 / 12 / 12 / 9

```
ә ғ қ ң ө ұ ү һ і          ← dedicated Kazakh row, full width
й ц у к е н г ш щ з х ъ
ф ы в а п р о л д ж э ё
⇧  я ч с м и т ь б ю  ⌫
123  🌐  ҚАЗ  ␣  енгізу
```

**Chosen design, and why.** All nine Kazakh-specific letters
(`Ә ә`, `Ғ ғ`, `Қ қ`, `Ң ң`, `Ө ө`, `Ұ ұ`, `Ү ү`, `Һ һ`, `І і`) sit on a
dedicated top row that spreads edge to edge, so each is ~37pt wide — wider than
a Cyrillic letter key. Nothing is hidden behind a long press.

The trade-off is one extra row: Kazakh keys are 39pt tall versus 46pt for EN/RU,
and the keyboard is 10pt taller. That was chosen over Apple's approach (3 rows +
long press on `а`, `к`, `н`, `о`, `у`, `г`, `х`, `и`) because `ә` and `і` are far
too frequent in Kazakh to sit behind a hold gesture. 39pt is still within the
native key-height band.

### Numbers / symbols

Two planes, `123` ⇄ `#+=`, with `₸` on the numbers plane and `€ £ ¥ $` on the
symbols plane.

## 7. Key behaviour

- Characters, space, return, shift and delete fire on **touch down**, like the
  system keyboard. `123`, `#+=` and the language key fire on touch up, because
  they rebuild the keyboard and must not tear the button out from under a finger.
- **Delete repeat:** 450ms hold, then one deletion every 85ms, cancelled on
  touch up, touch cancel or drag-out.
- **Shift:** one-shot; double tap within 350ms engages caps lock (`⇪`).
- **Auto-capitalization:** shift turns on at sentence starts when the host asks
  for `.sentences`. It only ever turns shift *on* — un-shifting happens once, at
  insertion — so a manual shift is never fought.
- **Double-tap space** inserts `. ` after a letter or digit.
- **Key click** via `UIDevice.current.playInputClick()`. This is the only reason
  `loadView()` is overridden and `ReplyInputView` exists; deleting both disables
  the sound and nothing else.
- Shift and delete get a 3pt hit-area expansion on the narrow Cyrillic grid.

### System keyboard switching — preserved

The globe key is wired with:

```swift
button.addTarget(self, action: #selector(handleInputModeList(from:with:)), for: .allTouchEvents)
```

which gives the exact system behaviour: **tap advances to the next keyboard,
long press opens the system input-mode list.** It is shown whenever
`needsInputModeSwitchKey` is true.

The separate `EN / РУ / ҚАЗ` key cycles only this keyboard's internal layout and
persists the choice in `UserDefaults` (the extension's own container — no App
Group was added).

## 8. Reply: exact text-acquisition strategy

`ContextTextProvider.acquire(proxy:hasFullAccess:)`, called **only** from the
Reply tap:

1. **`textDocumentProxy.selectedText`.** If the host exposes a selection inside
   the active editable input, that text is used. Source shown as *Selected text*.
2. **Explicitly copied text.** Requires Full Access, because `UIPasteboard` is
   unavailable to a keyboard extension without it. `UIPasteboard.general.hasStrings`
   is checked first — it is a metadata query and does **not** trigger the system
   paste prompt — and only then is `.string` read. Source shown as
   *Copied message*.
3. **Neither** ⇒ a localized status line that fades out after 2.6s and changes no
   geometry.

On success the **reply composer** opens (section 9).

### Clipboard policy

- Read **only** inside the Reply tap handler. No polling, no timer, no read on
  `viewDidLoad` / `viewWillAppear` / `textDidChange`.
- iOS 16+ shows its own *Allow Paste?* alert the first time per copy event. That
  prompt is not bypassed, and there is no public API for a keyboard to read
  arbitrary copied text without it.
- Message content is never logged. `ReplyLog` is `#if DEBUG` only and emits at
  most `Reply action invoked`, `selectedText available: false`,
  `clipboard string available: true, length: 127`.

### Full Access

`RequestsOpenAccess` stays `true` — it is genuinely required for step 2 and for
nothing else. Typing, `selectedText`, language switching and system keyboard
switching all work with Full Access **off**. The permission is mentioned to the
user **only** when it is the actual blocker (no selection *and* no clipboard
access), never as a permanent status. No network, no App Group, no other
entitlement was added.

## 9. Reply composer

Two texts, two fields, never mixed:

| | Holds | Written by | Reaches the host app |
| --- | --- | --- | --- |
| `sourceMessage` | the incoming message the user copied or selected | acquisition, once | **never** |
| `replyDraft` | what the user is about to send | deterministic simulator, then the user | yes, on Insert |

`ReplySession` in `ReplyContext.swift` is the model. The source is **never**
seeded into the draft: what the other person wrote must never silently become
what this user sends.

```
┌─────────────────────────────────────────┐
│ Ответ на:                        ⌄   ✕  │
│ Здравствуйте. Сможете завтра отпра…     │  ← read-only, 2 lines, ⌄ expands to 4
├─────────────────────────────────────────┤
│ Вариант ответа                         │
│ Yes, tomorrow works for me.   Вставить │  ← editable draft + Insert
└─────────────────────────────────────────┘
```

- The source is capped at 2 lines and truncated with `…`. The chevron appears
  **only when the text is actually truncated** and expands it to 4 lines.
- The draft grows from 34pt to 56pt (about 3 lines) and then scrolls.
- Insert is disabled and dimmed while the draft is blank.
- ✕ cancels: draft discarded, session cleared, keyboard returns to 272pt.
- The `return` key inserts a newline **into the draft** while composing, and is
  labelled `return` / `ввод` / `енгізу` rather than the host's `send`, so the
  host's return type can never be mistaken for a send action.
- Insert normalizes the draft and calls `textDocumentProxy.insertText(draft)`
  once. **Nothing is ever sent** — the messenger's own Send button stays under
  the user's control.

### How typing reaches the draft

`KeyboardViewController` routes every write through four helpers
(`targetInsert`, `targetDeleteBackward`, `targetTextBeforeCursor`,
`targetAutocapitalization`) that pick one of exactly two destinations: the host
field, or the composer. Nothing else in the key-handling code changed — shift,
caps lock, delete repeat, double-tap space and auto-capitalization all work
inside the draft too.

Draft edits are **storage-based**, not `UIKeyInput`-based:
`ReplyComposerView.insertText` / `deleteBackward` mutate the text and set
`selectedRange` explicitly, so typing is deterministic whether or not iOS grants
first responder to a view inside a keyboard extension. Delete is
composed-character aware, so emoji and combining marks delete whole.

First responder is still requested, because when the system grants it the user
also gets UIKit's caret, selection handles and magnifier for free. When it is
not granted, a blinking `fallbackCaret` positioned from `caretRect(for:)` draws
the insertion point instead, and a tap gesture positions the cursor via
`closestPosition(to:)`. **Which of the two paths you get is the one thing worth
watching on device (TEST G).**

The draft view's `inputView` is set to an empty `UIView` so the system can never
try to summon a second keyboard for it.

## 10. Direct incoming-message access — investigation result

**Reading an incoming WhatsApp / Telegram / Instagram Direct / Messenger /
iMessage message bubble is not available through the iOS Custom Keyboard API.**

`UITextDocumentProxy` is a view onto the **active editable text input** and
nothing else. There is no public API that hands a keyboard extension another
application's view hierarchy, its rendered content, or a selection made inside a
chat transcript. Keyboard extensions also run in a sandbox that cannot reach the
host app's process.

Mechanisms considered and their verdicts:

| Mechanism | Can it read an incoming bubble? | Notes |
| --- | --- | --- |
| `UITextDocumentProxy.selectedText` | **No** | Editable input only. Works for text the user selected in the *compose field*, and even there some hosts return `nil`. |
| System text-selection actions | **No** | The selection menu targets Share/Action extensions, not keyboards. Keyboards receive no such callback. |
| Explicit Copy → Reply | **Yes, this is the supported path** | Universal across every app that offers *Copy* on a message. |
| Share Extension | Partially, but not usable here | It can receive shared text, but it opens its own UI in a modal sheet and cannot hand data to a keyboard extension without an App Group and a separate user flow. Two extra taps, two extra context switches, and it only works where the host offers *Share* on a message. **Not implemented** — it would not improve the flow over Copy → Reply and would add an App Group + a second extension target to a project that is explicitly meant to stay stable. |
| Action Extension | Same as above | Same trade-off; same decision. |
| Accessibility APIs, screen scraping, OCR, screenshots, host view-hierarchy inspection, background clipboard monitoring | Not used | Explicitly out of scope. None appear anywhere in the source. |

**The supported universal workflow:**

```
long press the incoming message → Copy → focus the message field
→ switch to Reply Keyboard → tap Ответить
```

## 11. AI architecture

| Layer | Type | Lives in |
|---|---|---|
| Orchestration | `AIReplyService` | `Shared/AI/` |
| Prompt | `ReplyPromptBuilder` | `Shared/AI/` |
| Transport | `ReplyTransport` protocol | `Shared/AI/` |
| → direct | `DirectOpenAITransport` | `Shared/AI/` |
| → via server | `BackendTransport` | `Shared/AI/` |
| Credential | `SecureCredentialStore` (Keychain) | `Shared/AI/` |
| Settings | `AIConfiguration` (App Group, non-secret) | `Shared/AI/` |
| Errors | `AIReplyError` + `AIReplyStrings` | `Shared/AI/` |
| Keyboard flow | `ReplyFlowCoordinator` | `ReplyKeyboard/` |

`KeyboardViewController` contains no networking. The keyboard and the host app
generate replies through the same `AIReplyService`, so what you see in the app's
**Try a reply** screen is what the keyboard produces.

The model name appears in exactly one place in the iOS project —
`AIConfiguration.defaultModel` — and is overridable from Settings. No Swift file
elsewhere names a model.

The deterministic `ReplySimulator` that used to fake replies has been **deleted**.
A `MockReplyTransport` replaces it for offline work, behind `#if DEBUG` and
reachable only through an explicit `transportOverride`, so it cannot appear in a
shipping build.

### Optional backend

`backend/` is a zero-dependency Node service implementing the same contract:
`POST /v1/reply/generate`, the key in the environment, `OPENAI_MODEL`
server-side, per-client rate limiting, input caps, and token accounting that
records counts but never message text.

It is **not used by default**. Switch to it by setting a base URL and changing
`AIConfiguration.mode` to `.backend`. Run it with:

```sh
cp backend/.env.example backend/.env    # add your key
node backend/src/server.js
```

## 12. Voice input

Dictation is `DictationSheet`, wrapping the existing Apple Speech model. It is
available wherever text is entered: the profile, template instructions and the
try-a-reply message.

**Dictation runs in the host app, never in the keyboard extension.** An iOS
custom keyboard cannot reliably capture audio, and this project does not pretend
otherwise. The keyboard has no microphone button. To dictate a message and get a
reply, use **Try a reply** in the app.

Recognition uses the locale matching the app language (en_US / ru_RU / kk_KZ).
Where a locale is unavailable on the device it says so and you type instead.

  sign-in there. A free Personal Team can sign Debug with
  `Config/AIReply-NoAppleSignIn.entitlements` instead, with
  `AIREPLY_PUSH_NOTIFICATIONS = NO`. Enable *Sign in with Apple* for the App ID
  `kz.ai-reply.reply.keyboard.keyboard` in the portal.
* **Google** — Swift Package `GoogleSignIn-iOS` (9.x, resolved in
  `Package.resolved`). Set two build settings on the `AIReply` target:
  `GOOGLE_IOS_CLIENT_ID` (`<id>.apps.googleusercontent.com`) and
  `GOOGLE_IOS_REVERSED_CLIENT_ID` (`com.googleusercontent.apps.<id>`). They
  fill `GIDClientID` and the URL scheme in `Info.plist`. While they are empty
  (or do not match), Release builds hide the Google button instead of letting
  the SDK crash on a missing URL scheme; Debug builds show it and report it as
  unavailable.
* **Keyboard vibration** — Settings ▸ Keyboard ▸ *Vibration on key press*
  (on by default). The value is shared with the keyboard through the App Group
  and applies when Full Access is on.

Debug screenshots: launch with `-AIReplyDebugScreen signIn`, `email` or `code`.

Install:

1. Run the `AIReply` app on the iPhone once.
2. Settings ▸ General ▸ Keyboard ▸ Keyboards ▸ Add New Keyboard ▸ Reply Keyboard.
3. For the Copy → Reply test only: open Reply Keyboard in that list and turn on
   **Allow Full Access**. Typing tests do not need it.

### Push notifications

Firebase Cloud Messaging (Swift Package `firebase-ios-sdk` 12.x, products
`FirebaseCore` and `FirebaseMessaging`, linked to the app only — never the
keyboard). APNs carries the notifications; the server sends to the FCM
registration token. App side: `AIReply/Features/Notifications/`, the SDK only
in `FirebasePush.swift`.

Setup:

1. Firebase project `ai-reply-4bf8f` already has the iOS app
   `kz.ai-reply.reply.keyboard.keyboard` and a version-controlled client plist.
   Under *Project settings ▸ Cloud Messaging* upload APNs auth keys (.p8)
   for the required environments with their Key IDs and team ID `2PK6339Q47`.
2. Apple portal: enable *Push Notifications* for that App ID.
   `Config/AIReply.entitlements` has `aps-environment` (`development`; an App
   Store / TestFlight export re-signs it as `production`).
3. Give the app the Firebase options, either way:
   * use the shared `Config/Firebase/GoogleService-Info.plist`; the existing
     Firebase config build phase copies it into the main app only, or
   * set the build settings `FIREBASE_GOOGLE_APP_ID`, `FIREBASE_GCM_SENDER_ID`,
     `FIREBASE_API_KEY` and `FIREBASE_PROJECT_ID` on the `AIReply` target (not
     secrets; they ship in the app).

   While they are empty or malformed, the app does not configure Firebase and
   shows nothing about notifications. `AIREPLY_PUSH_NOTIFICATIONS = NO` turns
   push off for a build signed without `aps-environment`.

Behaviour:

* **Only after the legal consent.** `FirebaseMessagingAutoInitEnabled = NO`:
  before the consent no FCM token exists and nothing is registered.
  `FirebaseAppDelegateProxyEnabled = NO`: `AppServices` hands the APNs token to
  FCM itself and handles taps through its own notification delegate.
* **Only with a server that offers it.** `GET /api/v1/config` →
  `features.installations`, `push_notifications`, `preferred_language`. A
  missing key is "no": no registration, no card, no Notifications section.
* **Installation** (`POST /api/v1/installations`, provider `fcm`) after launch,
  sign-in (with the access token), sign-out (anonymous), a new FCM token, a
  permission or in-app switch change and a language change — only when
  something differs from the last accepted registration, else once a day. A 401
  refreshes the session once; failures back off. The logout request carries
  `X-Installation-ID` (no other request does).
* **Installation id.** A random UUID in the Keychain
  (`AfterFirstUnlockThisDeviceOnly`) in the app's own access group
  (`<team>.kz.ai-reply.reply.keyboard.keyboard`), so the keyboard cannot read
  it. The FCM token is kept with the installation it was handed to.
* **Permission.** Never asked at launch. Home shows a soft card to a signed-in
  user while it is undetermined; Settings ▸ Notifications has the iOS status,
  the in-app switch and the account's categories (security always on).
* **Taps.** `aireply://<screen>` opens that screen (unknown → Home);
  `https://ai-reply.kz/...` opens in an in-app browser; anything else just opens
  the app. A destination waits behind consent, sign-in and onboarding (15
  minutes at most). A tap with a delivery id is reported to
  `POST /api/v1/notifications/opened`.
* **Language.** The account's `preferred_language` (the language of its
  notifications) follows a language picked in Settings, and is set from the
  app's language when the account has none; it never overwrites a choice made
  on another device.

DEBUG only: `-AIReplyForcePushCard YES` shows the card and the Settings
section whatever the state; `-AIReplyOpenLink subscription` (or a full link, or
`web`) opens a link at launch like a tapped notification;
`-AIReplyDebugProvisionalPush YES` gets provisional permission without an
alert so `xcrun simctl push` is delivered, and `-AIReplyDebugAutoOpenPush YES`
treats it as tapped; `-AIReplyDebugScreen notifications` opens Settings at the
notifications section.

## Аккаунты и тарифы (сервисный режим)

Приложение умеет работать в двух режимах, переключатель — **Настройки ▸ Где создаются ответы**:

| Режим | Кто держит ключ | Аккаунт | Лимит |
|---|---|---|---|
| `direct` — «Свой ключ» | пользователь, в Keychain | нет | нет |
| `backend` — «Сервис AI Reply» | сервер (`ai-reply-back-end`) | телефон/почта + код | тариф, дневная квота |

В сервисном режиме приложение по умолчанию ходит только на сервер:
`https://ai-reply.kz`. Плоский `http://` разрешён только для локальных
адресов во время разработки.

### Как это ведёт себя

- Гейт входа появляется **только** в сервисном режиме с указанным адресом. Существующая
  установка со своим ключом продолжает работать как раньше — никакого экрана входа.
- Access-токен живёт 15 минут. Обновление идёт через актор `AccountSession`, поэтому
  приложение и клавиатура не могут запустить две ротации одновременно (сервер считает
  повторное использование refresh-токена кражей и закрывает сессию).
- Токены лежат в Keychain с access group = App Group, поэтому клавиатура использует
  ту же сессию и не просит войти второй раз.
- Пока пользователь не вошёл, сервисный режим использует старый install-token путь —
  уже установленные сборки не ломаются.
- Ответ `/api/v1/ai/reply` приносит свежую квоту, она кэшируется в App Group и
  показывается на главном экране и в настройках. Источник истины — всегда сервер.
- В клавиатуре текст ошибки зависит от режима: «проверьте ключ» только в `direct`,
  «войдите в приложении» и «ответы на сегодня закончились» — в сервисном.
