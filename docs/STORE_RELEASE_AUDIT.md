## 5. Стратегия подписок

### 5.1 Что было (по коду и живому серверу 08.10.2026)

- В базе три тарифа: Free (7 ответов в день), Standard (`199000` тиын = 1 990 ₸, 30 в день), Pro (`349000` = 3 490 ₸, 50 в день). Цены и лимиты приходят с сервера, в приложениях они не захардкожены.
- В приложениях есть экран «Тариф» со списком тарифов и кнопкой «Выбрать». Кнопка вызывала `POST /api/v1/payments/checkout`, а затем сразу `/confirm`. На сервере единственный провайдер — `DemoProvider`: `VerifyPayment` всегда возвращает `succeeded`, и он подключался при любом `PAYMENT_MODE`, включая `live`. Итог: любой пользователь одним нажатием или двумя API-запросами получал Pro на 30 дней без оплаты и мог продлевать это бесконечно повторным `/confirm`. Ему же приходили push и письмо «Подписка активирована, спасибо».
- StoreKit и Google Play Billing не реализованы ни на одной платформе. Внешних ссылок на оплату нет, так что anti-steering сейчас не нарушен.
- Прод отдаёт `payment_mode: "demo"`.

Для стора это прямой отказ: Apple 3.1.1 и 2.1, Google Play Payments и Misrepresentation. Кроме того, это обход бесплатного лимита за счёт расходов на OpenAI.

### 5.2 Решение для первого бесплатного релиза (реализовано)

1. **Тарифы управляются из админки.** Флаги «Активен» (тариф можно выдавать) и «Виден в приложении» (новый `plans.is_visible`, миграция `0012_plan_visibility.sql`), плюс название, описание, лимиты, цена, период. Миграция при деплое скрывает платные тарифы, Free остаётся видимым. Ни тарифы, ни подписки, ни платежи не удаляются.
2. **`GET /api/v1/plans`** отдаёт только активные и видимые тарифы. У каждого есть поле `purchasable`, в ответе есть `purchases_enabled`. Лендинг использует тот же список. Кэша нет: изменение в админке приложения увидят при следующем запросе, без новой версии.
3. **Переключатель «Покупки»** (`system_settings.purchases_enabled`, карточка в Настройках админки). Он включается только при наличии проверенной биллинг-интеграции (`payments.Provider.Live()`), а её пока нет. Демо-провайдер может «продавать» только на сервере разработки с явным `PAYMENT_DEMO_CHECKOUT=true` и `PAYMENT_MODE=demo`. В production это запрещено валидацией конфига.
4. **Сервер решает сам.** `checkout` отказывает для скрытого, выключенного, архивного, бесплатного или несуществующего тарифа (`409 PLAN_UNAVAILABLE`), а также когда покупки выключены (`403 PURCHASES_DISABLED`). Это работает и для старых сборок, и для прямых запросов. Незавершённый демо-платёж нельзя подтвердить после выключения покупок. Повторный `confirm` идемпотентен.
5. **Существующие подписчики** сохраняют тариф и лимит до `expires_at`: entitlement не смотрит на видимость. Экран «Тариф» показывает им текущий тариф и срок. После окончания срока пользователь автоматически переходит на Free.
6. **Тариф по умолчанию (Free)** нельзя выключить, сделать платным или заархивировать (`400`, причина `default_plan`): на нём держится регистрация. Скрыть его можно.
7. **Приложения.** В Release-сборках кнопки покупки нет вообще: ни StoreKit, ни Play Billing ещё нет, и включаемый сервером путь оплаты в обход IAP был бы «скрытой функцией» по Apple 2.3.1. Список тарифов показывается, только если в нём есть что-то кроме текущего тарифа. Цена показывается только у реально покупаемого тарифа. В Debug-сборках демо-покупка доступна для разработки.

### 5.3 Как потом включать платные тарифы

1. **iOS — StoreKit 2.** Продукты в App Store Connect (одна группа подписок для Standard и Pro), покупка в приложении, отправка `Transaction`/`appTransactionID` на сервер. Сервер проверяет транзакцию через App Store Server API и принимает App Store Server Notifications v2 (продление, отмена, возврат, grace period). Нужна кнопка «Восстановить покупки» и ссылка «Управлять подпиской» (`showManageSubscriptions`). На пейволе по Schedule 2 DPLA: цена, период, автопродление, ссылки на Terms of Use и Privacy Policy.
2. **Android — Google Play Billing Library 8+.** Покупка, отправка `purchaseToken` на сервер, проверка через Google Play Developer API (`purchases.subscriptionsv2`), Real-time Developer Notifications через Pub/Sub, acknowledge в течение 3 дней. Ссылка на управление подпиской в Google Play.
3. **Сервер.** Новые реализации `payments.Provider` (`appstore`, `googleplay`) с `Live() == true`. `subs.Assign(source = "app_store" | "google_play")` только после проверки. Идемпотентность по ID транзакции и маппинг продуктов на тарифы. Таблицы `payments` и `subscriptions` уже есть.
4. **Альтернативный биллинг.** Для Казахстана ни у Apple (External Purchase / Link Entitlement), ни у Google (User Choice Billing, External Offers) программ нет: Казахстан не входит в списки стран. Поэтому в приложениях только IAP и Play Billing, никаких ссылок на оплату картой или через Kaspi.
5. **Порядок включения:** реализовать провайдер → проверить в sandbox → в админке сделать тарифы видимыми → включить «Покупки» → выпустить версию приложений с UI покупки. Видимость без оплаты разрешена, но показывать платный тариф без возможности купить его в приложении рискованно для ревью. Админка об этом предупреждает.

### 6.2 Что данные получает OpenAI

`internal/ai/provider.go` вызывает OpenAI Responses API (`POST /v1/responses`, `store: false`, модель из `OPENAI_MODEL`, по умолчанию `gpt-4o-mini`). Идентификатор пользователя не передаётся. Состав запроса:

- **developer-сообщение:** только правила сервера и значения из перечислений: язык, правило рода, тон, длина, эмодзи;
- **user-сообщение:**
  - роль и «О себе»;
  - бизнес (предложение, описание, до 8 правил);
  - название и инструкции персоны;
  - рабочие часы (текущее локальное время и расписание);
  - **входящее сообщение (скопированное или выделенное)**;
  - инструкция;
- **«Написать»:** запрос плюс правило рода;
- **«Умная коррекция»:** текст инструкции;
- **«Ремонт» качества:** сгенерированный ответ, не больше одного раза.

Отображаемое имя, e-mail, телефон и ID пользователя не отправляются. Ошибки провайдера не логируются вместе с телом запроса. Отказ от обучения на данных и ZDR — это настройки аккаунта OpenAI, их нужно проверить вручную (11.1).

### 6.5 Удаление аккаунта

- **В приложениях:** Настройки → Аккаунт → «Удалить аккаунт» и экран согласия. Подтверждение и полная локальная очистка: токены, кэш, согласие, выученные слова, профиль.
- **iOS:** для Apple-аккаунтов сначала повторная авторизация Apple. `authorization_code` уходит на сервер, сервер обменивает его и отзывает токен (`appleid.apple.com/auth/token` → `/auth/revoke`). Отмена пользователем прерывает удаление. Другие сбои Apple не мешают удалению.
- **На сервере** (`DELETE /api/v1/me`, `POST /api/v1/me/delete`), одна транзакция:
  - коды OTP по адресам пользователя удаляются;
  - установки отвязываются, push-токен очищается;
  - строка `users` удаляется, каскадом уходят профиль, способы входа, устройства, сессии, подписки, счётчики, события, платежи, согласия, уведомления, жалобы;
  - идентификаторы пользователя убираются из фильтров кампаний.

  Тест проверяет ноль строк во всех таблицах с `user_id` и 401 для обоих токенов.
- **Веб** (требование Google Play): `https://ai-reply.kz/account/delete` (и `/delete-account`). E-mail → 4-значный код (назначение `delete`) → удаление. Ответ одинаковый для существующих и несуществующих адресов.
- **Сохраняется:** только агрегаты без идентификаторов. Записи `admin_audit_logs` об админ-действиях хранят ID записи, но не e-mail.

### 6.6 Безопасность передачи и хранения

- HTTPS везде: нет исключений ATS и cleartext, Release-сборки обращаются только к `https://ai-reply.kz`.
- HSTS при https-адресе, Secure-cookie админки.
- Токены лежат в Keychain и Keystore. Push-токены зашифрованы AES-GCM. OTP хранятся как HMAC, refresh-токены как хэши.
- Логи: запрещённые ключи вычищаются (`internal/logging`), тела запросов не логируются. Тесты `TestMessageContentIsNeverPersisted` и `TestAdminAPINeverExposesContent`.
- Права доступа: каждый защищённый запрос перечитывает пользователя. Удалённые и отключённые получают 401/403. Все изменяющие запросы админки требуют сессию и CSRF.
## 7. Авторизация и push-уведомления

### 7.1 Авторизация

Новый вход (e-mail OTP через Resend, Google, Apple) сделан грамотно. Это подтверждено чтением кода и тестами `internal/auth/...`, apptest auth/email/provider/link:

- **e-mail OTP:** `crypto/rand`; HMAC, привязанный к назначению и адресу; TTL 5 мин; 5 попыток считаются атомарно; одноразовое закрытие; пауза 32 с между запросами на сервере; часовой и суточный лимиты на адрес из БД; ответы не раскрывают, существует ли аккаунт;
- **Google и Apple ID-токены:** проверка по JWKS (только RS256), `iss`, `aud` (наши client id), `exp`/`iat`/`nbf`, обязательный nonce;
- **токены сессии:** access-JWT подписан HS256 с фиксированным алгоритмом; refresh-токены случайные, хранятся только как HMAC, ротируются с обнаружением повторного использования;
- **каждый защищённый запрос** перечитывает пользователя и отклоняет отключённых и удалённых;
- **админка:** PBKDF2 на 600 тыс. итераций, хэшированные сессии, CSRF на всех изменяющих запросах.

## 8. Письмо-подтверждение подписки

### 8.1 Архитектура (уже реализована в ветке notification)

```
активация подписки (payments.Confirm / admin AssignPlan)
   └─► notifications.Events.activated(...)  — ключ идемпотентности subscription_activated:<source>:<id>
          └─► notifications (UNIQUE dedupe_key) + notification_deliveries (push и e-mail, уникальный индекс на e-mail)
                 └─► воркер outbox (lease, будится сразу и раз в 2 с)
                        └─► Resend API (Idempotency-Key, 1 повтор на 5xx внутри запроса)
                               └─► статус доставки, число попыток, код ошибки без PII
```

- **Идемпотентность:** повторные колбэки, повторный `confirm` и параллельные воркеры не дают второго письма. Тест `TestPaymentConfirmationNotifiesOnce`.
- **Повторы:** ограничены, 5 попыток (5 с / 30 с / 2 мин / 10 мин), с джиттером и учётом `Retry-After`. Состояние видно в `notification_deliveries`.
- **Независимость от оплаты:** ошибки письма не влияют на оплату и подписку. Письмо пишется в outbox после коммита подписки, best-effort вызовом.
- **Логи:** адрес читается только в момент отправки. В логах и в тексте ошибки нет ни адреса, ни кода.
- **Локализация:** kk/ru/en/uz, по `users.preferred_language`. Бренд «AI Reply», название тарифа, дата окончания, лимит.

### 8.4 Реалистична ли цель «письмо в течение 60 секунд»

Путь письма: активация подписки → строка в outbox → воркер → Resend API → почтовый сервер получателя.

| Участок | Чем определяется | Оценка |
|---|---|---|
| Покупка → сервер узнал о ней | StoreKit 2 / Play Billing: приложение отправляет транзакцию на сервер сразу после покупки. App Store Server Notifications v2 и Google RTDN приходят асинхронно и могут задерживаться | при отправке из приложения обычно секунды. Только по серверным уведомлениям возможны минуты, и это вне нашего контроля |
| Проверка транзакции у Apple/Google | App Store Server API / Play Developer API | обычно меньше 1–2 с, при сбоях провайдера дольше |
| Активация → запись в outbox | код сервера | миллисекунды. Сейчас уведомление пишется после коммита подписки отдельным вызовом, а сверка недостающих уведомлений добавлена в 15-минутный цикл (см. 8.3) |
| Outbox → Resend | воркер просыпается сразу по сигналу, запасной опрос раз в 2 с, повторы 5 с / 30 с / 2 мин / 10 мин | обычно 1–3 с. Худший случай: в этот момент идёт большой пакет кампании |
| Resend принял → письмо во входящих | очередь Resend, MTA получателя, антиспам, для Apple Private Relay ещё пересылка Apple | обычно секунды, иногда минуты. Не гарантируется |

**Вывод.** На стороне сервера, от подтверждённой активации до передачи письма в Resend, 60 секунд реалистичны с большим запасом: типично 1–3 с. Гарантировать 60 секунд «до входящих» нельзя: доставку контролируют Resend и почтовый провайдер получателя, а при покупке только через серверные уведомления Apple/Google задержка зависит от них. Для мониторинга есть статус и время каждой доставки в `notification_deliveries` (`provider_accepted`, число попыток, код ошибки). Отказы и жалобы Resend пока не обрабатываются (P3, нужен webhook).
