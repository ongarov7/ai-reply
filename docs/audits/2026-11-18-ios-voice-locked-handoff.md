# Locked-device voice result handoff

The snapshot writer uses `.atomic` with `.completeFileProtectionUnlessOpen` (Data Protection Class B). This lets the main app create the encrypted result while the iPhone is locked, before it releases its background execution time. The write is synchronous and the store retains no file descriptor. A closed snapshot cannot be reopened until the device unlocks. The keyboard then reads the existing file when it appears, without requiring the main app to resume. The three-minute result expiry, App Group access, backup exclusion, and absence of audio files remain unchanged.

Apple documents that [complete protection](https://developer.apple.com/documentation/foundation/nsdata/writingoptions/completefileprotection) rejects reads and writes while protected data is unavailable, whereas [protected unless open](https://developer.apple.com/documentation/foundation/nsdata/writingoptions/completefileprotectionunlessopen) permits new file creation while locked. Its [file protection documentation](https://developer.apple.com/documentation/foundation/fileprotectiontype/completeunlessopen) specifies that a closed Class B file cannot reopen until unlock. Apple also documents that [atomic writes](https://developer.apple.com/documentation/foundation/nsdata/writingoptions/atomic) write an auxiliary file before replacing the destination. The distinction between Class A and Class B is described in [Apple Platform Security](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web).

The previous Class A write could fail after the phone locked. The controller kept the response in memory but released its background task immediately afterward. Depending on an unlock observer to retry is not a durable handoff: Apple's [protected-data notification](https://developer.apple.com/documentation/uikit/uiapplication/protecteddatadidbecomeavailablenotification) documents availability, not a guarantee of background launch or execution. Apple explains the limits of execution after background work ends in [Extending your app’s background execution time](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time).

Automated tests cover successful atomic replacement, restoration from another store instance, expiry, backup exclusion, and the requested file-protection attribute when the runtime exposes it. These tests do **not** demonstrate hardware Data Protection or locked-device behavior. Physical verification still needs a passcode-protected iPhone: wait until protected data becomes unavailable, finish the result while locked, verify that the write succeeds and a new read fails, then unlock and open the keyboard in the conversation without foregrounding AI Reply. Verify the result within its three-minute lifetime. Include an existing Class A snapshot in that test to check migration of the destination path.
