## 0. Коротко

1. **Логика слотов Pro (1 мобильный + 1 десктоп) на сервере сделана правильно**: слот держит частичный уникальный индекс БД, захват идёт в `BEGIN IMMEDIATE`, гонок нет, проверка стоит до резерва кредитов во всех четырёх AI-путях.
2. **Включать strict нельзя: сейчас он заблокирует всех Pro-пользователей.** Ни один выпущенный клиент (iOS, Android, новый macOS) не передаёт `installation_id` при входе, а macOS вообще не регистрирует установку. У сессий нет подписанной привязки `iid`, и каждый Pro-запрос получит `PRO_DEVICE_IDENTITY_REQUIRED`. Пока iOS не обновляется, strict для iOS невозможен в принципе (§2, PRO-1).
3. **Shadow-режим уже работает в production и пишет строку в `pro_device_events` на каждый Pro-запрос, без очистки** (PRO-3). Это нагрузка на единственный writer SQLite и мусор в журнале безопасности админки.
4. **macOS 1.0.1 (ещё не опубликован) меняет обычную генерацию**: при включённом на сервере флаге каждый запрос уходит с `output_char_limit=400`, а длинный ответ превращается в ошибку (MAC-1). Шаблон «Свой стиль» на сервере работает как «Коллега» (MAC-2). Сохранение профиля может молча удалить только что добавленный документ (MAC-3). Инструкции к разговору обрезаются первыми (MAC-4). Это нужно исправить до публикации DMG.
5. **Документы (62 запроса по 31 реалистичному файлу): верно только 16.** Самое опасное:
   - цена, посчитанная формулой, выбрасывается, а **закупочная цена, маржа и поставщик уходят в модель** — она может назвать клиенту закупку (RET-1);
   - длинная строка нужного товара молча пропускается, и модель получает **цену другого товара** (RET-2).
   Импорт устойчив к враждебным файлам (zip-бомбы, XXE).
6. Атакующие тесты Pro-лимита (§3.4): инвариант «1 + 1» не сломался ни разу. Но устройство, авторизованное **позже**, может навсегда отозвать телефон владельца (F3). iPhone, восстановленный из бэкапа, теряет Pro без возможности восстановления через админку (F1).

Итог по релизу:
- **Бэкенд** можно держать задеплоенным при `PRO_DEVICE_LIMIT_ENABLED=false`, но shadow нужно разгрузить (PRO-3/F5) или выключить строго значением `PRO_DEVICE_LIMIT_SHADOW_MODE=false` (`off` и `no` не сработают, F12).
- **macOS 1.0.1** стоит публиковать только после исправлений MAC-1…MAC-4 и RET-1/RET-2.

## 3. Pro-лимит устройств

### 3.1 Как это реально работает сейчас

```text
вход (VerifyOTP/Apple/Google) ──► issueSession: devices row (по device_id клиента)
     │                              iid = HMAC(installation_id)  ← клиенты его НЕ шлют → iid = ""
     ▼
writeSession ──► Authorize(...)   (ошибка игнорируется)
POST /installations (с токеном) ──► BindInstallation: link device_id ↔ installation
AI-запрос ──► generate ──► Authorize ──► bound? = link есть И iid из JWT совпал
                │                         strict: нет → 403 PRO_DEVICE_IDENTITY_REQUIRED
                │                         shadow: нет → событие в pro_device_events (каждый раз)
                ▼
            ClaimProDevice: слот (user, category) свободен → authorization; занят → 403 LIMIT
```

Слот привязан к строке `devices` (per-user), а не к установке. Строка `devices` нестабильна: смена аккаунта A→B→A, переустановка, потерянный `device_id` создают новую строку.

### 3.2 Находки по Pro-лимиту

**PRO-1 · P0 (блокер включения strict) — привязку не делает ни один клиент**
- Доказательство: macOS — ни одного `installation_id`/`/installations` в `AirReplyKit/Sources`; `SessionStore.swift:55-70` хранит только `device_id`, который затирается каноническим id сервера. iOS — тело входа `AI-Reply/Shared/Account/AccountService.swift:159-171` содержит `device_id`, `platform` и т. д., но не `installation_id`. Android шлёт `X-Installation-ID` только при выходе (`AccountSession.kt:157-163`).
- Сервер: `iid` берётся только из тела входа (`auth/service.go:335-346`), `bound` требует его (`prodevices/service.go:86-97`).
- Последствие: при `ENABLED=true, SHADOW=false, CLIENTS_READY=true` **каждый** Pro-запрос с iOS, Android и macOS получит 403 `PRO_DEVICE_IDENTITY_REQUIRED`. Десктопный слот реальный macOS-клиент не займёт никогда.
- Исправление: клиенты шлют стабильный `installation_id` при входе и в заголовке каждого запроса и регистрируют установку сразу после входа, до первой генерации. Так как iOS сейчас не трогаем, strict для мобильной категории невозможен до следующего релиза iOS. Предлагаю per-category включение (PRO-11): сначала только `desktop`.

**PRO-2 · P1 — привязка возможна только при входе, refresh её не «апгрейдит»**
- `auth/service.go:461,495` копирует `stored.InstallationIdentity`. Даже обновлённый клиент со старой сессией останется непривязанным, пока пользователь сам не выйдет и не войдёт. Это принудительный перелогин всех Pro.
- Исправление: при refresh (или при аутентифицированной регистрации установки), если у семейства refresh-токенов `installation_identity = ''`, а запрос несёт `installation_id`, который уже привязан к этой строке `devices`, — записать привязку в семейство (trust-on-first-use). Безопасность не страдает: `installation_id` всё равно генерирует клиент, а владение refresh-токеном и есть доказательство.

**PRO-3 · P1 (сейчас в production) — shadow пишет событие на каждый Pro-запрос, очистки нет**
- `prodevices/service.go:93-97` → `reject()` → `RecordProDeviceEvent` (`:158`) — отдельная пишущая транзакция и Info-лог при **каждом** запросе с непривязанной сессией, то есть со всех нынешних клиентов. При `multiple=true` (`:103-105`) — ещё одна запись. То же при каждом входе и refresh (`auth_handlers.go:167-169`).
- `PRO_DEVICE_LIMIT_SHADOW_MODE` по умолчанию `true` (`config/pro_devices.go:21`). В `repository/retention.go` нет ни `pro_device_events`, ни `pro_device_observations`, ни `pro_device_notification_jobs`.
- Последствия: неограниченный рост таблицы, лишний захват единственного writer'а SQLite на горячем пути (конкурирует с резервом кредитов), блок «Recent device security events» в админке забит `identity_missing · shadow`.
- Исправление: в shadow писать агрегаты (одна строка на (user, device, kind) за окно 15 мин или сутки, со счётчиком), а не событие на запрос; добавить retention (например, 90 дней событий, 30 дней обработанных jobs). Быстрая мера до исправления — `PRO_DEVICE_LIMIT_SHADOW_MODE=false`.

**PRO-4 · P1 — данные shadow завышают нарушения**
- `ObserveProDevice` (`pro_devices.go:347-381`) считает все строки наблюдений категории за всё время: не учитывает давность, отзыв, удалённые и дублирующиеся строки `devices` одного телефона. После любой смены телефона или A→B→A `count > 1` навсегда.
- Исправление: считать различные установки, активные за последние 30 дней, без отозванных; отдавать отчёт «аккаунтов с >1 активной установкой в категории».

**PRO-5 · P1 (для strict) — отзыв вечный, восстановить нельзя ни пользователю, ни админу**
- `UNIQUE (user_id, device_id)` (`0031:16`) + повторный вход на той же установке возвращает ту же строку `devices` (`auth/service.go:339-342`, `UpsertDevice`) → `previous.RevokedAt != nil` → навсегда `PRO_DEVICE_REVOKED` (`prodevices/service.go:108-112`). В админке есть только «Revoke», «Reactivate» нет.
- Сценарий: пользователь освободил старый телефон, чтобы попробовать новый, и вернулся — Pro на старом телефоне больше не заработает. Ошибочный отзыв админом тоже не отменить без ручного SQL.
- Исправление: различать `released` (можно снова занять, когда слот свободен) и `blocked` (только админ), добавить админ-действие «Вернуть доступ».

**PRO-6 · P1 (для strict) — самообслуживания нет, а тексты обещают его**
- Ни один клиент не вызывает `GET/DELETE /api/v1/me/pro-devices`. Ошибка macOS (`issue.pro_device_limit`) и письмо (`email.pro_device_limit.manage`) советуют «освободить прежнее устройство с авторизованного устройства». Сделать это негде, остаётся только поддержка.
- Исправление: экран «Устройства Pro» во вкладке «Аккаунт» macOS (и позже в iOS/Android/на сайте). Лучше — перенос Pro на текущее устройство с подтверждением кодом из e-mail и лимитом переносов (PRO-11).

**PRO-7 · P1 (для strict) — A→B→A и конфликт привязок блокируют собственный телефон**
- Без `installation_id` при входе возврат в аккаунт A создаёт новую строку `devices` (`UpsertDevice`: id принадлежит B → новый id). Слот A занят старой строкой → `LIMIT_REACHED` на своём же Mac или телефоне.
- Привязки, созданные уже сейчас в shadow (iOS/Android регистрируют установки с токеном), мешают привязать новую строку: `UNIQUE(user_id, installation_id)` → `ON CONFLICT DO NOTHING` → `ErrProDeviceIdentity` (`pro_devices.go:254-276`). Решать это предлагается «вручную», но инструмента нет.
- Исправление: при конфликте для того же пользователя, платформы и установки переносить привязку на новую строку (или переиспользовать старую строку и её авторизацию); на клиентах — `installation_id` при входе.

**PRO-8 · P2 — продуктовые последствия, которые стоит подтвердить**
- iPad (`ipados`) и iPhone — одна мобильная категория: на Pro нельзя пользоваться обоими.
- На заблокированном втором устройстве Pro-пользователь не может потратить и купленные пакеты: запрос режется до выбора корзины (`ai/service.go:241-247`). Текст ошибки об этом не говорит.
- Платформу объявляет клиент: модифицированный клиент займёт десктопный слот с телефона. Это ограничение модели без аттестации (P3).

**PRO-9 · P2 — голосовой ввод на macOS показывает общую ошибку на Pro-коды**
- `VoiceError` не знает `PRO_DEVICE_*` → `.server(code:)` → «voice.issue.server». Для strict нужно то же объяснение, что и для генерации.

**PRO-10 · P3 — мелочи**
- `Error.Details()` всегда `allowed_devices: 1`; для `uz` сообщения падают на английский (`prodevices/service.go:242-273`).
- Старый `DELETE /me/devices/{id}` для уже отозванной авторизации отвечает `ok`, но строку `devices` не отзывает (`service.go:221-232` → `Revoke` возвращает `nil` досрочно).
- `make test-race` упирается в таймаут `apptest` (см. §1).

**PRO-11 · рекомендация по модели (вместо точечных заплаток)**
1. Идентичность — `installation_id` (случайный UUID): iOS/macOS — Keychain `ThisDeviceOnly`, Android — `noBackupFilesDir` (уже есть), Windows — файл под DPAPI. Передаётся при входе, refresh и в заголовке `X-Installation-ID`.
2. Слот = (user, category) → **установка**, а не строка `devices`. Повторный вход, смена аккаунта и новые строки `devices` на той же установке слот не теряют.
3. Привязка «апгрейдится» на refresh (PRO-2) — без принудительного перелогина.
4. `released` вместо вечного `revoked`; `blocked` — только админ.
5. Самообслуживание: «Pro сейчас на “iPhone 15” (2 дня назад). [Перенести Pro сюда]» с кодом из e-mail; не больше 2–3 переносов на категорию за 30 дней — это и есть защита от передачи аккаунта.
6. Включение по категориям: `PRO_DEVICE_LIMIT_ENFORCE=desktop` — сначала macOS (и будущий Windows), мобильную категорию держать в shadow до релиза iOS с `installation_id`.
7. Shadow — агрегаты и отчёт в админке, retention.

### 3.3 Что сделано хорошо

Слот держит БД, а не предпроверка; `ClaimProDevice` проверяет и строку `devices`, и платформу внутри транзакции; повторные запросы с того же устройства не плодят строк; `TouchProDevice` пишет не чаще раза в 15 минут; IDOR при отзыве закрыт (`a.id=? AND a.user_id=?`); заблокированное устройство не может отозвать владельца слота (`pro_devices.go:206-215`); админ-отзыв идёт с ролью, CSRF, обязательной причиной и аудитом в той же транзакции; конфиг не даёт включить strict без `CLIENTS_READY` и уведомления без strict.

### 3.4 Атакующие тесты на копии бэкенда

Отдельно написано 1 569 строк атакующих тестов на копии бэкенда (оригинал не тронут, `-race`, 0 гонок). Повторный прогон: 12 тестов `TestAdv_*` и 2 `TestAdvConfig_*` падают воспроизводимо. Исходники и вывод — `docs/audits/evidence/2026-11-03-pro-device-adversarial/`.

**Главное: инвариант слотов устоял.** Ни один путь не дал аккаунту больше одного активного мобильного или десктопного слота и не дал Pro без авторизации в strict:
- 16 установок одновременно захватывают слот через reply, refresh, регистрацию и вперемешку → ровно 1 победитель на категорию;
- 24 захвата через 4 соединения → 1 + 1;
- отзыв против захвата — 40 раундов в обоих порядках;
- 15 подделок платформы (`web`, `""`, `iOS`, `IOS`, `ios\x00`, `darwin`, `win32`…) → 403 без захвата;
- заголовки `X-Installation-ID`, `X-Device-ID` и поле `platform` в теле не меняют подписанную привязку;
- отзыв чужого аккаунта закрыт на всех трёх маршрутах;
- отказ не тратит пакет, не сжигает Idempotency-Key и не трогает подписку;
- уведомления: дедупликация (30 одновременных отказов → 3 уведомления), повторы ограничены 10.

## 4. AI Context: сервер

**CTX-B1 · P1 — сервер может отклонить запрос, который клиент считает допустимым, и пользователь видит «ошибку сервера»**
- Сервер ограничивает весь `prompt.User` (исходное сообщение + инструкция + служебные обёртки + HTML-экранированный контекст) 4096 байтами (`ai/mac_context.go:100-108`). Клиент отводит под профиль и фрагменты `3072 − байты(запроса)` и не учитывает обёртки и экранирование (`ContextProfiles.swift:226`). Ответ `400 INVALID_REQUEST field=context` клиент превращает в `.server` (`Generator.swift:56-64`) и предлагает «Повторить», что детерминированно падает снова.
- Исправление: сервер выбрасывает фрагменты с конца, пока не влезет, и сообщает об этом, а не падает; отдельный код `CONTEXT_TOO_LARGE` с подсказкой; клиент считает тот же бюджет.

**CTX-B2 · P2 — HTML-экранирование портит названия**
- `html.EscapeString` для профиля и фрагментов (`mac_context.go:92,96`) превращает `"`, `'`, `&` в `&#34;`, `&#39;`, `&amp;`, а политика требует «сохранять названия и числа точно». Риск ответов вида «Кофе &#34;Арабика&#34;», «M&amp;M&#39;s»; к тому же текст раздувается (CTX-B1). Остальные блоки (`incoming_message` и др.) не экранируются — подход непоследователен.
- Исправление: экранировать только последовательность закрывающего тега (`</context_` → `<\/context_`) или использовать случайную границу блока.

**CTX-B3 · P2 — порядок и разметка контекста в промпте**
- Блоки контекста дописываются **после** «Write only the message.» (`prompt.go:233` + `mac_context.go:90-98`), без вводной строки, без даты импорта и версии файла. Правило «спроси при конфликте фактов» модели нечем подкрепить: какой прайс новее, она не видит.
- Исправление: ставить контекст перед `incoming_message`, у каждого фрагмента — «файл · лист · дата импорта», более новые первыми; финальная строка — последней.

**CTX-B4 · P2 (не проверено на проде) — `MaxOutputTokens = 400/600` подменяет админский лимит токенов**
- `mac_context.go:110`. С `gpt-4o-mini` (значение по умолчанию, `config.go:558`) это безопасно. Если в production выбрана reasoning-модель, рассуждения съедят лимит и ответ придёт пустым или обрезанным. Нужно проверить `OPENAI_MODEL` в production; токены лучше выводить из символов с запасом и не опускать ниже админского значения.

**CTX-B5 · P3** — для compose с `template_id=custom` подсказка ссылается на `<template_instructions>`, которого в compose нет (`prompt_rules.go:82`, `compose.go:61-63`).
**CTX-B6 · P3** — `MAC_CONTEXT_INPUT_TOKEN_BUDGET` на деле бюджет в байтах: переименовать или задокументировать.
**CTX-B7 · заметка** — функции контекста закрыты условием `sessionPlatform == "macos"` (`mac_context.go:37`). Для Windows-клиента нужно добавить `windows`.

**MAC-1 · P1 (регрессия обычной генерации) — каждый запрос получает жёсткий лимит 400 символов**
- `generationOptions` всегда ставит `outputCharacterLimit: outputLength.rawValue` (`.standard = 400`) и `recipient`, если сервер объявил `mac_context_generation` (`QuickBarModel.swift:403-411`, `ContextProfiles.swift:197-200`). Сервер видит `output_char_limit != 0` → весь mac-путь: политика, лимит 400 символов, `MaxOutputTokens=400` (у compose было не меньше 700 — `compose.go:155-163`, у reply — админское значение, по умолчанию 180), проверка бюджета (`mac_context.go:29-33,85-112`). Если модель после исправления всё ещё длиннее, `Complete` возвращает `ErrOutputCharacterLimit` (`quality.go:371-375`). Это 502 `AI_OUTPUT_LIMIT_EXCEEDED`, а клиент показывает общую ошибку.
- Затрагивает любое сообщение macOS, даже без профиля и документов, при включённом флаге на сервере (по handoff он включён в production).
- Исправление: отправлять `output_char_limit` и `context` только когда пользователь их выбрал; «Обычный» = поле не отправляется (поведение сервера по умолчанию).

**MAC-2 · P1 — «Свой стиль» = «Коллега», и два конфликтующих выбора адресата**
- `DesktopTemplate.custom.recipient = .work` (`QuickBarModel.swift:20-27`). Reply шлёт `template_id: recipient.rawValue` (`Generator.swift:131`), compose — `options.recipient` (`:167`). Сервер применяет подсказку «Replying to a COLLEAGUE…».
- В режиме ответа одновременно видны меню шаблонов (Друг / Деловой / Клиент·Продажи / Свой стиль) и чипы адресата (Друг / Клиент / Коллега / Партнёр). Клик по «Коллеге» показывает в меню «Деловой» (`QuickBarModel.swift:258-266`). В мобильных приложениях единый набор Друг/Клиент/Коллега/Партнёр.
- Исправление: один ряд адресатов, как на мобильных; «свой стиль» — часть профиля (поле «Стиль/инструкции»), без подмены адресата.

**MAC-3 · P1 (потеря данных) — сохранение профиля откатывает добавленные или удалённые документы**
- Редактор копирует профиль целиком, вместе с `attachments`, в момент `beginProfileEdit()` (`QuickBarModel.swift:413-416`). Кнопка «Добавить документ» доступна при открытом редакторе. Импорт сохраняет профиль уже с новым документом (`:504-507`), а затем «Сохранить» записывает старую копию (`:418-432`, `ContextProfiles.swift:108-114` — замена по id). Новый документ молча исчезает; удалённый — возвращается.
- Исправление: редактор сохраняет только поля-метаданные, слитые с текущим профилем из хранилища; на время редактирования прикрепление блокировать или сливать.

**MAC-4 · P1 — инструкции «для этого разговора» обрезаются первыми и молча**
- Поле обещает «до 1000 символов» (`bar.context.instructions`, счётчик `AdvancedContextView.swift:79-86`). Текст дописывается в **конец** поля «Preferences» профиля (`QuickBarModel.swift:405-408`), а весь профиль режется до `min(1000, доступно)` **байт** по словам (`ContextProfiles.swift:223-228`). Кириллица — 2 байта на символ, то есть около 500 символов на весь профиль. Поэтому при заполненном профиле инструкция к разговору не доходит совсем, а без профиля режется после примерно 490 символов. Порядок полей тоже ставит «Политики», «Описание» и «Предпочтения» последними.
- Исправление: отдельное поле запроса (`context.instructions`, ≤500 символов, с приоритетом) или резервирование бюджета под него первым; индикатор «что уйдёт в AI» с метром байтов; приоритет полей: Инструкции → Политики → Товары/Услуги → Компания → Описание.

**MAC-5 · P2 (приватность) — сохранённые профили и прайсы видны любому аккаунту на этом Mac**
- Хранилище одно на пользователя macOS (`ContextProfiles.swift:67-72`). При смене аккаунта очищается только выбор (`QuickBarModel.swift:514-528`), после выхода профили остаются в списке. Второй человек, вошедший на этом Mac, видит и использует чужие бизнес-профили и каталоги.
- Исправление: файл и ключ на аккаунт (`profiles-<userID>.aicontext`); при выходе — выбор «оставить на этом Mac / удалить»; профили другого аккаунта не показывать.

**MAC-6 · P2 — все ошибки импорта сводятся к одному тексту**
- `catch` → `bar.context.import_failed` (`QuickBarModel.swift:509-511`): «не прочитан, проверьте формат, 8 МБ, сканы». Не различаются защищённый паролем PDF, `.xls`/`.doc`, пустое извлечение, лист только из формул, превышение 2 млн символов, переполнение хранилища (32 MiB), Keychain.
- Исправление: типизированные ошибки импортёра → конкретный текст и что делать; после успешного импорта — сводка: «3 листа, 1 240 строк, 12 ячеек с формулами пропущено».

**MAC-7 · P2 — разрушительные действия без подтверждения**
- «Удалить профиль» удаляет его вместе со всеми документами без вопроса (`AdvancedContextView.swift:170`, `QuickBarModel.swift:434-446`). Удаление документа — тоже. Смена профиля в списке молча выбрасывает несохранённые правки (`AdvancedContextView.swift:129`).

**MAC-8 · P2 — не видно, что повлияло на ответ**
- Карточка результата не показывает, какой профиль и какие строки ушли в модель. Нет предупреждения «в документах ничего не найдено» или «строка не поместилась и пропущена». Список вложений не отличает «сохранено в профиле» от «только сейчас» (`AdvancedContextView.swift:187-214`).

**MAC-9 · P2 — временные настройки живут дольше разговора**
- `customInstructions` и длина ответа не сбрасываются ни после копирования, ни при сбросе через 10 минут (`resetConversation`, `QuickBarModel.swift:200-209`), а временные документы сбрасываются. Указание «дай скидку 10%» для одного клиента незаметно уйдёт и в следующие ответы. Индикатор — только точка у «AI Context».

**MAC-10 · P2 — карта ошибок**
- `INVALID_REQUEST` с полями `context`/`output_char_limit`/`template_id` и `AI_OUTPUT_LIMIT_EXCEEDED` → `.server` → общий текст и «Повторить» (`Generator.swift:56-64`, `QuickBarView.swift:519-520`), хотя повтор в первом случае бесполезен.

**MAC-11 · P2 — доступность**
- Кнопки-иконки без `accessibilityLabel`: «изменить/создать профиль», «новый профиль», «удалить документ» (должна называть файл) — `AdvancedContextView.swift:130-137,206-209`. `contextIssue` не озвучивается VoiceOver. Поля редактора без постоянных подписей: placeholder пропадает после ввода. Фиксированные ширины (сегменты 210 и 300 pt) рискуют обрезать kk/ru. Заголовок «AI Context» не переведён в ru/kk. Пояснения кеглем 11,5 pt вторичного цвета.

**MAC-12 · P2 — плотность интерфейса**
- Над полем ввода теперь постоянный ряд (режим + шаблон + AI Context + аккаунт), а редактор профиля (11 полей) втиснут в прокручиваемую область 245 pt внутри плавающей панели. Это отход от утверждённого минималистичного «Spotlight-like» бара (`Docs/DESIGN.md`). План — §7.

**MAC-13 · P2 (тесты) — snapshot-тесты рисуют ключи вместо строк**

## 7. План улучшения UX (macOS)

Цель: бар снова «вопрос → ответ за 2 секунды», а контекст — понятный, видимый и проверяемый.

```text
┌──────────────────────────────────────────────────────────────┐
│ ✦ Ответьте клиенту, что доставка завтра…            🎙  [↑] │  ← ввод — первая строка
│ [Друг] [Клиент] [Коллега] [Партнёр]                          │  ← один выбор адресата
│ 👤 Мой магазин ▾   📎 Прайс_ноябрь.xlsx ✕   ＋ Документ   ⋯  │  ← строка контекста (если включён)
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ Добрый день! iPhone 15 Pro 256 ГБ — 649 990 ₸, в наличии 3 шт│
│ Источники: Прайс_ноябрь.xlsx · Лист «Телефоны» · 2 строки ▸  │  ← что ушло в модель
│ ⚠ «Доставка» в документах не найдена — проверьте срок        │  ← нет данных → предупреждение
│                                   [Другой вариант] [Копировать]│
└──────────────────────────────────────────────────────────────┘
```

1. **Бар.** Поле ввода — первым. Режим «Сообщение/Ответ» определять автоматически (есть скопированный текст → «Ответ»); ручной переключатель оставить, но не первым элементом. Меню шаблонов убрать, адресаты — одним рядом чипов, как на iOS/Android.
2. **Строка контекста** (только когда что-то выбрано): чип профиля, чипы документов с пометкой «сохранён в профиле» или «только сейчас», «＋ Документ», меню «⋯» (длина ответа, очистить). Кнопка «Контекст» с бейджем количества вместо мелкой надписи «AI Context»; перевести заголовок.
3. **Профили — в окно настроек**, новая вкладка «Профили»: форма во всю ширину, подписи над полями, группы «О вас», «О бизнесе», «Правила (доставка, возвраты, оплата)», «Стиль и инструкции». Счётчики по полям и **превью «Что увидит AI»** с метром бюджета — видно, что будет отрезано. Документы профиля: таблица «файл · листы · строки · пропущено формул · дата импорта · [Обновить] [Удалить]».
4. **Инструкция к разговору** — отдельное поле с подписью «только для этого ответа», сбрасывается после «Копировать» или нового разговора; бюджет резервируется под неё первым (MAC-4).
5. **Доказательства в ответе:** «Источники: …» с раскрытием до строк; «не найдено в документах: …»; если строка пропущена из-за бюджета — сказать об этом.
6. **Импорт:** конкретные ошибки и итоговая сводка (MAC-6), прогресс для больших файлов, повторный импорт «обновить из файла» с датой.
7. **Безопасность действий:** подтверждение удаления; «Сохранить изменения?» при смене профиля или закрытии.
8. **Доступность:** ярлыки VoiceOver для всех иконок (с именем файла), озвучивание ошибок (`AccessibilityNotification.Announcement`), порядок фокуса «ввод → адресаты → контекст», проверка kk/ru/en в снимках (MAC-13).

Порядок работ:
1. До публикации DMG: MAC-1…MAC-4, RET-1, RET-2 и CTX-B1/RET-10.
2. MAC-5, MAC-6, MAC-8, MAC-10, RET-4…RET-9.
3. Перенос профилей в настройки и превью «Что увидит AI».
4. Доступность и снимки трёх локалей.

Для Pro: PRO-3/F5 сразу (это production), затем модель PRO-11 вместе с F1, F3, F4 — до любого включения strict.
